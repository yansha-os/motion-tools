# Animation review in v1

The harness keeps a short loop: make a draft, inspect it, watch it, answer questions, and revise. Your feedback decides what changes. A version is accepted only after you choose to keep it.

## First review

1. Run `npm.cmd run app`. Choose a configured provider, connect the updated Studio plugin, select a rig, and choose it under **Target rig**.
2. Generate a draft with **Preview, inspect, and ask me for feedback** checked, or pick an existing library clip and click **Inspect & ask me**.
3. Watch the Studio preview. Use **Preview selected** to replay it. The panel's front and side diagrams help locate measured poses; they do not show the rendered character.
4. Answer the questions and choose **Keep this version**, **Refine it**, or **Try a different approach**. Write what should stay and what should change, confirm that you watched the preview, and save your feedback.
5. For refinement, click **Make the requested changes**. The harness sends your original brief, the reviewed recipe, your answers, keep/change notes, and inspection findings to your chosen provider. It saves a new child version and inspects it again.

Older clips stay in the library. **Preview previous version** replays the parent of the current revision. Selecting an older clip restores its saved review. To reconsider an accepted version, start a new inspection for that version.

## What gets inspected

The Studio plugin evaluates a detached, anchored clone with the same joint evaluator used by animation preview. It samples up to 128 distinct times, including contact boundaries and midpoints, evenly spaced poses, up to 15 authored marker times, and both clip endpoints. Inspection supports up to 96 nodes and requires edit mode. It restores the original model's Archivable setting and destroys its clone even when sampling fails.

The report includes body rise/drop and horizontal displacement, estimated foot clearance and near-ground movement, and endpoint position and velocity differences for loops. Ground comes from the rig's rest-pose bounds. It is not a raycast against your map. Foot naming is heuristic, and skinned bone rigs have no measured foot sole thickness.

Choose the intended motion mode before inspecting:

| Mode | Interpretation |
| --- | --- |
| In place | The game supplies travel. Backward foot movement is not automatically a sliding defect. |
| Contains travel | Sampled travel is reported, but the harness cannot infer the game's intended speed. |
| Stationary | Large movement near the estimated ground may indicate an unwanted contact shift. |
| Not sure | Report measurements and uncertainty without assuming planted feet. |

Sampling can miss short events between samples. No flags does not mean a good animation. Inspection does not simulate gameplay, gravity, cloth, hair, mesh deformation, or collisions. Joint positions also cannot describe every change in hand or foot orientation.

## Optional AI critique and screenshots

AI pose review is enabled by default in the panel. When Studio samples are available, it adds one provider call with a 2,500 output token limit. Uncheck it to use the local measurements and standard questions only. You can also click **Ask AI to inspect this evidence** manually.

The critique must cite supplied sample IDs or attached image IDs. Invalid references, invented prior finding IDs, and malformed responses are rejected without a retry. Every persisted finding receives a server-derived `interpretation`: `measured_issue` for pose samples, `observed_issue` for exact reviewed-recipe captures, `reference_target` when it cites any unbound user image, or `excluded_evidence` when a legacy record cites a known mismatched capture. An explicit incompatible model label is rejected; older responses without this field receive the safe derived label. A reference target can guide motion toward a user-provided pose, but it cannot be stated as an existing defect in the reviewed animation. A linked child review must revisit every earlier finding as `addressed`, `still_present`, or `uncertain` and cite fresh evidence. This is an evidence comparison, not a quality score; the critique cannot set the acceptance status.

For screenshots bound to the exact reviewed recipe, the critique also receives frame-specific authored context: normalized clip progress, nearby authored markers, active declared contacts, and nearby contact boundaries. The AI can use this to know which beat or declared support window a frame was intended to represent, but the metadata is not proof that the beat is visible or that contact occurred. Unbound user images do not receive recipe-derived timing context because their time labels are unverified. Exact-image context follows the same screenshot into proposal previews and same-provider revision notes; unbound references continue to omit it, and both handoffs label it as authored intent rather than observation.

Every new machine-actionable patch proposal must point to a zero-based `findingIndex` in that same critique response, and its evidence must be a subset of that exact finding's source and evidence IDs. Proposal preview repeats the linked finding alongside the candidate recipe, so the AI can check the rationale before asking to apply the edit. Legacy proposals without a finding link remain readable but cannot be previewed; rerun the critique to obtain a grounded proposal.

For image-cited proposals, proposal preview also returns the exact screenshot hash, view/time/focus and joint-map caveat, plus the persisted per-image observation and its limitation (or `not_assessed` for legacy records). The live proposal evaluator carries these same references into each result, allowing the AI to reason from the screenshot assessment that supports the edit without treating the note as the image itself.

The evaluator also returns `visualFollowUp`. When cited screenshots have times, reproducible Studio camera views, and a joint-map fingerprint consistent with the live evaluation, exact reviewed-recipe captures receive `matched_frames_ready` with candidate frames and the expected recipe fingerprint. Unbound user images receive `reference_only`: they may guide a target comparison but are not a before-state or proof a defect was fixed. After screenshot preflight and user permission, the agent can retrieve the exact candidate recipe with proposal preview, capture it on the same rig, then inspect the candidate PNGs alongside cited images under the indicated interpretation. Missing times, unsupported manual `detail` views, or a mismatched name-map fingerprint are explicitly marked `manual_match_required`; the agent must not fabricate a camera or rig-map match. This schedules a visual comparison but does not decide whether the change is artistically better.

For newly captured images, Studio also returns the resolved source-joint → rig-joint map produced by the same `Authoring.tracks` call that evaluates the screenshot pose. The server compares this receipt with the queued recipe and map and rejects missing or mismatched receipts before caching the image. `jointMapping.fingerprint` identifies the complete supplied map; `jointMapping.appliedFingerprint` identifies only the authored channels actually resolved for that recipe. This detects stale/incompatible capture plugins and prevents requested mapping metadata from being mistaken for proof of which names the renderer used. It still does not prove anatomical equivalence or local-axis retargeting.

Rig inspection separately returns `aiRigSummary.captureFocusEligibleJointNames` for rendered close-ups. The server includes a name only when Studio's eligibility hint agrees with the validated driven-joint hierarchy and the exact parent, and the node carries plausible, non-fully-transparent `BasePart.Size` evidence. This intentionally excludes non-driven roots, Bone-only nodes, contradictory or incomplete metadata, and fully transparent parts. Use this allow-list when requesting `focusJoints` from a capture planner. Studio validates the name against the selected rig before requesting screenshot permission and checks it again on the posed clone, so the inspection list is planning guidance rather than a substitute for runtime validation.

When a capture-plan request includes `focusJoints`, pass the same inspection's `sessionId` and `rigId`. The server checks those names against the fresh active-rig inspection before returning the plan. A rig-bound plan also returns `expectedRigSignature`; pass it with the frames to the capture tool so any topology change since planning is rejected before Studio work is queued. If the plan follows a candidate evaluation, pass the evaluator's signature into the planner too; the planner rejects a rig that changed between sampling and planning. Built-in blueprint, candidate-evaluation, editor-draft, and partial-capture recovery guidance carries the same signature through subsequent capture/retry calls. Candidate and editor-draft capture tools accept this guard. Plans without a rig binding or close-ups can remain offline and rig-independent. This prevents plans from advertising detail frames that the later capture would reject and keeps capture evidence tied to the reviewed topology.

The saved-animation and unsaved-candidate planners also return `jointMapFingerprint`, a SHA-256 fingerprint of the exact source-to-rig name map used to choose active channels and close-up moments. Pass it as `expectedJointMapFingerprint` to the matching capture tool together with that exact `jointMap`; the server rejects a changed map before queueing. Native capture provenance retains the bounded exact map, validates it against the fingerprint, and carries it through review attachment so partial-review retry arguments can reuse the same mapping. Older reviews that contain only rename summaries remain readable but cannot safely reconstruct a retry map; re-plan from the live rig instead of guessing. This keeps visual planning, capture, and recovery on the same channel interpretation, in addition to recipe and topology guards. It does not prove semantic equivalence between differently named joints or convert local axes.

Rig-bound saved-animation and candidate plans also return up to four `focusJointSuggestions`, limited to exact names in the fresh inspection's part-backed capture allow-list and active authored channels. Unless explicit `focusJoints` are supplied, the plan schedules up to two suggestions by default, limited by the requested frame budget, while preserving at least two whole-rig moments per view. Suggestions cite declared-contact or measured-motion cues when available, and the close-up time prefers that joint's measured cue over a generic key; `scheduledByDefault` shows which suggestions are already in `frames`. These are evidence-selection aids, not defect labels or an artistic diagnosis. Editor-draft capture continues to accept explicit `focusJoints`.

Single-animation capture planners accept up to 31 exact `priorityTimes`, enough for every distinct internal start, midpoint, and end time across a 16-phase blueprint. Supply them in importance order; the plan schedules as many as the view/frame budget allows before optional close-ups and ordinary cues, and `priorityTimeCoverage` lists requested, scheduled, and omitted times in that order. Blueprint guidance asks the AI to rank exact boundaries and midpoints from the associated phase intents, pose changes, and contact/release transitions rather than choosing the first six chronologically. For omitted times, the planner also returns ready-to-use `priorityTimeCoverage.followUpBatches`: each batch is an exact `frames` array, retains every requested view, and contains at most eight frames. Execute each unchanged with the same recipe, joint map, fingerprints, and rig signature; omit `priorityTimes` when explicit frames are supplied. Stills remain frame-local evidence and do not prove semantic intent or motion between frames.

The same priority-time path is available for automatic capture of the live unsaved editor draft. Its follow-up instructions additionally preserve the editor asset ID, draft recipe/fingerprint, and loaded-source fingerprint (when available), so omitted beats can be inspected without silently switching to a different draft or source animation.

For a visual critique, attach screenshots of the exact version under review. The browser resizes PNG, JPEG, or WebP files to PNG, at most 960 pixels on the longer side. The server accepts up to eight images per review, each at most 1.5 MB and 2048 pixels per side. Images are fingerprinted and checked again before transmission. They go to your selected provider only when you click **Ask AI**. Use an image-capable model; support depends on your account and model ID.

Editor-draft screenshot capture carries both the exact draft fingerprint and, when available, the loaded source fingerprint from the same `motion_studio_read_editor_draft` result. Pass that `sourceFingerprint` as `expectedLoadedSourceFingerprint`; Studio checks it before and throughout capture, and the MCP server rejects a capture that does not confirm the expected source. Each returned image and durable review attachment records `loadedSourceRelation` as `matches_loaded_source`, `modified_since_loaded_source`, or `unknown`; later review reads, critique context, and proposal previews keep that provenance visible. The server derives attachment provenance from its own short-lived capture record and rejects caller-forged values. This helps an AI distinguish an unchanged source pose from unsaved viewport edits; it is identity evidence, not evidence that the motion is artistically correct. When the read reports no source fingerprint, omit the guard and treat the relationship as unknown.

When the configured critique provider receives screenshots, its response must include exactly one `visualObservations` entry per supplied image ID, with `assessment: observed` or `assessment: inconclusive`, visible evidence, and a limitation of that still. The model also receives deterministic `pixelSignal` diagnostics for extreme uniformity/transparency; these signals are stored with the image SHA-256 and surfaced in `visualEvidenceAudit`, proposal evidence, and revision context. Warnings are only a cue to inspect legibility, and no warning proves the rig is readable. The server rejects missing, duplicate, unclassified, or unrelated image IDs. An inconclusive image cannot support a visual finding or resolve a prior finding as `addressed`/`still_present`; that follow-up must remain `uncertain` unless legible evidence is captured. Persisted records are checked against the same rule. `motion_review_read` exposes this disposition per image; legacy critiques without it remain labeled `legacy_unclassified`. This is an auditable model response, not independent proof that the observation is correct; inspect the PNGs yourself and treat uncertain or occluded details as unknown.

`motion_review_read` also returns a deterministic `visualEvidenceAudit`: planned frame coverage and matched image IDs, per-image assessment status, attached images excluded from critique, and the image IDs that remain unassessed. Each image is classified as `matches_reviewed_recipe`, `unbound_user_image`, or `mismatched_reviewed_recipe`. Known mismatched native captures are excluded even when no storyboard was planned; unbound user images remain available as visual references, but cannot prove the exact reviewed recipe pose. The audit includes explicit still-image limitations. This separates capture completeness from AI visual assessment; neither metadata coverage nor a model-generated observation proves quality or what happened between frames.

When a user requests a refinement, the saved critique's per-image observations are passed into the authoring prompt as `visualEvidenceNotes`, along with the original image IDs and limitations. They are explicitly treated as fallible text summaries—not as the images or verified facts—and cannot override the user's requested changes or the preserve-what-was-liked rules. If the requested change depends on visual information the note cannot establish, the agent must ask for fresh visual review rather than infer it.

When the child review is linked to that exact parent, its critique context also retains the parent's screenshot observations with the parent review revision, image hashes, view/time, focus joint, and recipe identity where available. These are historical model-generated notes, not a substitute for retrieving the old PNG or inspecting fresh child screenshots. Follow-up findings must cite only evidence from the current child review; a hash identifies the old image but does not mean that image was supplied to the critique. For a prior `reference_target`, `observed_issue`, or user-request finding, `addressed`/`still_present` requires at least one fresh screenshot bound to the exact child recipe. Unbound images may be referenced, but alone they cannot establish the child state; use `uncertain` when there is no exact rendered evidence.

For a prior measured finding, a follow-up based on fresh pose samples is labeled `measured_change_only`: it reports what changed or persisted in the sampled spatial data, not whether the animation looks better or fulfills the artistic intent. An unbound screenshot alone cannot resolve a measured finding either; use fresh pose samples or an exact child-recipe capture. Persisted follow-ups expose `evidenceInterpretation` (`measured_change_only`, `exact_child_capture`, or `unresolved`) so later AI steps can keep those claims distinct. This remains evidence bookkeeping, not visual acceptance.

`motion_studio_capture_views` normally requests 2–8 unique angle/time frames (front, side, back, three-quarter, or overhead) from a connected Studio plugin. It also accepts a one-frame request for retrying one missing target. Named angles are rig-relative, so a rotated/custom rig is still captured from its anatomical front/side rather than a fixed world axis; camera roll follows rig-up, with rig-forward used as screen-up for overhead. It asks Studio for screenshot permission, temporarily poses an isolated clone and moves the camera, then restores the prior camera. This native screenshot path remains experimental and must be tested in the current Studio runtime; a successful API response is not proof that the image is well-framed or shows the intended pose. First retrieve the successful capture IDs together with `motion_studio_read_candidate_captures` and inspect the rendered images as the calling AI agent. Then attach the exact returned frame metadata in one `motion_review_attach_captures` call; it fetches and verifies bounded chunks locally, validates recipe/rig/time identity, and fingerprints the PNGs without copying image bytes through the conversation. Manual screenshots remain available if native capture is unsupported.

`motion_studio_read_candidate_captures` keeps `sequenceGroups` strict to each capture batch for honest coverage accounting. It also returns `temporalContinuityGroups`, which can join frames across different batches only when the source, exact recipe fingerprint, rig topology, view, focus joint, and editor-draft identity match. Every frame retains its capture-batch ID; incompatible captures (including changed drafts or rigs) never combine. This lets an agent add a targeted frame later and inspect its placement against compatible earlier timestamps without losing provenance. The group reports the widest gap and an optional midpoint time, but even a dense set of stills cannot prove interpolation, smoothness, or what happened between captures.

The saved, candidate, and editor-draft capture planners accept up to four `focusJoints`, using exact animated node names from `motion_studio_inspect`. Rig-bound saved/candidate plans automatically select up to two inspected eligible targets when the caller does not specify them; offline plans do not invent rig targets. If authored channel names differ from rig-node names, pass an exact source-to-rig `jointMap`; the plan returns that same map for the capture call. A target must have an active base track, enabled nonzero-weight layer track, or root-motion channel after mapping; disabled and zero-weight layers cannot trigger a close-up of motion that is not visible. The planner reserves room for close-ups after preserving at least two whole-rig moments for each requested view. It prefers a target's own measured motion cue, then its authored key moments and matching declared action moments; `focusJointCoverage` lists requested, scheduled, and omitted names, while `omittedDetails` explains each omission (`not_in_recipe`, `inactive_channel`, `frame_budget`, or `no_scheduleable_moment`). Studio still checks that a scheduled node is an exact part-backed node on the active rig; Bone-only targets cannot be tightly framed. Focused frames are complementary evidence and do not replace whole-rig views.

Mandatory clip-start/end frames are retained as whole-rig framing anchors, but they do not count as complete interior coverage of a moment category. Under a tight frame budget, an endpoint contact therefore cannot suppress a later contact boundary from storyboard selection. Once the planner has selected its highest-priority motion cue, its remaining category-aware slots favor cues from distinct moving joints before generic uniform samples; one joint's repeated peaks are less likely to consume the whole interior storyboard. Shared timestamps can cover multiple joints at once. The schedule remains bounded and deterministic; omitted authored beats remain disclosed in `omittedMomentSummary`.

For saved-animation capture jobs, the server validates every returned frame against the exact saved recipe fingerprint, active rig topology, and ordered requested schedule. The job returns explicit complete/partial coverage and missing view/time pairs. A captured frame must still be attached to its matching review; read that review's `visualCaptureCoverage` before critique. A successful job does not mean the images have been inspected by the AI.

When a planned review remains partial, `motion_review_read` and `motion_review_attach_captures` also return `visualCaptureRetry`. If verified attached captures establish one consistent joint map and the review has a live session, rig, and topology signature, its `ready` result includes exact `motion_studio_capture_views` arguments for only the missing frames, bound to both the reviewed recipe fingerprint and rig signature. Pass those arguments unchanged after capture preflight; the capture tool rejects a changed rig before queuing work. If mapping evidence is absent, incomplete, or conflicting, the handoff says `needs_mapping` or `mapping_conflict` instead of inventing a map. The descriptor is a safe execution request, not visual evidence: capture, retrieve and inspect each PNG, attach it at the latest review revision, then reread coverage before critique.

Unsaved-candidate and exact editor-draft capture jobs return `captureCoverage` with the requested schedule, verified captured view/time pairs and capture IDs, exact missing pairs, and an explicit `complete` or `partial` status. A complete capture set is not yet AI-visible: retrieve and inspect every listed PNG with `motion_studio_read_candidate_captures` (1–8 frames in one response) or use `motion_studio_read_candidate_capture` for an individual frame. The batch reader returns no images unless every requested image verifies and the aggregate byte limit is met; on failure it identifies the exact captures to retry. For a partial capture, keep its successful IDs and retry only `captureCoverage.missingFrames` against the identical recipe fingerprint and rig. Attach the retry images together with the earlier images, then require complete review-level `visualCaptureCoverage`; successful metadata from separate capture batches can jointly satisfy the planned review. Capture coverage verifies schedule and metadata, not composition, framing, or visual quality.

Image readers also return a bounded `pixelSignal` summary: sampled color variation, dominant-color share, luminance variation, transparency, and conservative warnings for near-uniform or mostly transparent images. Treat this only as a transport/visibility hint; it does not judge composition, pose quality, anatomy, or intent. Always inspect the actual PNG, and do not discard a capture solely because a warning appears.

Grouped AI-visible screenshot reads keep whole-rig frames separate from exact joint close-ups, even when they share a camera angle and timestamp. Each group reports its expected/missing schedule and an explicit temporal-sampling summary (first/last sample, largest time gap, and sampled normalized-progress range). These values make unobserved intervals easy to spot; they do not establish what happened between stills or turn coverage into an animation-quality score.

For an exact linked child revision, `motion_review_read_comparison_images` returns up to four paired parent/child PNGs to the calling AI agent. It only matches checksum-verified native captures from the exact parent and child recipes, same rig ID/topology and viewport dimensions, identical view/focus, and normalized clip progress within 1/60; the parent frame must have been assessed as visually observed. It returns no partial images when the byte budget is exceeded and never treats manual references, mismatched captures, or inconclusive parent images as a valid before frame. Inspect both images: a pair is a like-for-like still comparison, not evidence of motion between frames or automatic improvement. Cite only the child image ID as current evidence; the parent image is historical context. If no pair is returned, recapture matching times/views through the normal Studio permission flow instead of assuming correspondence.

To verify a revision, record user feedback on the parent review, create the immutable child, then start a review for that child with `compareReviewId` set to the parent review ID. Add fresh Studio samples and/or screenshots, then request an AI critique. The response must account for every carried-forward finding using evidence from the child. An `addressed` label is a model assessment, not user acceptance; the user still watches and decides.

When both reviews contain pose samples from the same rig and matching joint hierarchy, the child record also includes a normalized-progress trajectory comparison. It reports the joints with the largest sampled position changes and cites sample IDs separately for parent and child. A duration change is aligned by clip progress, not wall-clock seconds. This is a change map, not an improvement score; it cannot determine whether a pose better satisfies the user's intent.

VFX uses parameter checks and user questions. An attached screenshot can support a visual critique, but v1 does not sample or simulate particles, beams, or energy columns for analysis.

## Persistence and failures

Reviews are immutable numbered snapshots under `artifacts/reviews/<review-id>/`. They contain the asset fingerprint, samples, findings, questions, screenshots, feedback, and child version link. Generation provenance remains under `artifacts/generations/`. These folders are local and ignored by Git.

Submitting an old review revision is rejected. Editing a recipe file outside the library invalidates its old review. A generation reservation prevents two requests from consuming the same feedback simultaneously. If generation cannot start, feedback remains available to retry. Restarted operations recover to a state requiring feedback or a retry, never acceptance.

Cancel stops an inspection or critique and cancels Studio commands that have not been delivered. It cannot undo a delivered preview or guarantee that a provider stops billing work already performed. Use **Stop** to stop an active Studio preview.

MCP clients use `motion_review_start`, `motion_review_read`, `motion_review_read_images`, `motion_review_feedback`, `motion_review_critique`, and `motion_review_attach_capture(s)`. After reconnecting, `motion_review_read_images` can return 1–8 persisted screenshots together, with each image paired to checksum-verified metadata and the exact review revision. Inspect these PNGs as the calling agent before requesting a separate configured-provider critique; pass the same revision to critique, and reread review/images if it changed. Critique calls may be billed. A child review can be linked to its exact parent using `compareReviewId`. Feedback supplied through MCP is labeled `client_reported_user`; the server cannot independently verify the conversation.

For a linked child review, `motion_review_critique` can optionally set `includeMatchedParentImages: true` to send up to four exact, checksum-verified parent/child screenshot pairs to the selected provider for frame-local visual comparison. This is off by default because it sends additional image data and may increase provider cost. The persisted `comparisonVisualEvidence` audit records each pair, image fingerprint, and binary provider order. Child screenshots remain the only current visual evidence; parent screenshots are historical context only and cannot be cited in findings, follow-ups, or `visualObservations`. Still pairs do not establish motion quality or improvement.
