# Authoring workflow

The workflow keeps creative intent attached to the work. It runs locally and uses the AI already connected to the MCP server. It neither includes a hosted model nor calls another provider.

## Start and resume

Reload the Motion Tools MCP connection after building the updated server. The Studio plugin does not need reinstalling for this change. Ask the client:

> Start a Motion Tools workflow for this request. Keep my exact wording, record my references and what each should guide, and separate requirements from things to avoid. Inspect the references before creating a rough candidate. Review that candidate before detailing it.

Use `motion_workflow_start` with a `brief`. Its fields are `name`, `kind` (`model`, `animation` or `vfx`), `request`, `approach`, `requirements`, `avoid`, and `references`. Requirements have a unique `id` and `description`. References have an absolute local `path` and `useFor` annotation. Use an empty reference list when no reference exists; do not invent one.

Use separate workflows for the model, animation and effect, with the same shared art direction where appropriate. `motion_workflow_list` finds sessions after a restart. `motion_workflow_read` returns the brief, history, current revision and next stage, plus an ordered `next.actions` playbook containing relevant MCP tool names, purpose and preconditions. These are advisory only: the agent still checks the live tool schema, reads the returned evidence, obtains user decisions where needed, and calls tools explicitly. No action runs automatically, and an absent suggestion does not mean a capability is unavailable. Before reporting progress, the workflow reader validates persisted structure and SHA-256 integrity, contiguous revision snapshots, stage order, complete requirement/exclusion review coverage, failure corrections, and evidence lineage. Integrity detects accidental/schema-valid edits but is not an authenticated signature. In `motion_workflow_list`, `offset` pages valid workflows and `invalidOffset` separately pages corrupt-record diagnostics; use `invalidRecordCount` and `nextInvalidOffset` to detect more failures. Invalid entries are not counted as valid workflows. Pass the current workflow revision to every mutation. If a stale write fails, read the workflow again before making another decision.

## Attach the work and inspect it

Before complex edits or a plugin reload, preserve unsaved work with an editor checkpoint. Read the actual open draft with `motion_studio_read_editor_draft`, poll its job with `motion_studio_job`, and use the returned `checkpointHandoff` for `motion_editor_checkpoint_create`. The server accepts only the completed read’s exact recipe fingerprint and matching session/rig; arbitrary supplied recipes are not checkpoint inputs. The snapshot includes recipe, playhead, dirty/candidate flags, parent/source metadata, and rig topology. It preserves that read snapshot even if subsequent edits change the live editor. This is explicit checkpointing, not automatic autosave, a library revision, or an export.

Checkpoints live under `artifacts/editor-checkpoints`, survive server restarts, and appear as compact metadata in `motion_agent_resume` (`checkpointLimit` defaults to 5). `motion_editor_checkpoint_list` and `motion_editor_checkpoint_read` verify immutable records and report corrupt entries separately. Repeating the same completed read and metadata is idempotent; different metadata cannot overwrite its checkpoint. File fingerprints detect content/identity changes, not authenticated authorship.

Checkpoint summaries identify the captured rig by `rigId`. Optional `sourceRigName` describes the animation’s source profile, which may belong to a different rig after retargeting; use a fresh inspection to identify the current recovery target.

To find recovery candidates beyond the recent resume list, call `motion_editor_checkpoint_list` with the inspected `rigSignature`; optionally combine `dirty` and captured `rigId` filters. Filters apply before pagination, and `total` counts matching verified records. After reconnecting, prefer topology filtering because the target rig UUID may have changed. Summaries include captured `rigSignature`; a match still needs the normal restore preview and fresh driven-joint inspection. Corrupt-record diagnostics cover the whole store because an unreadable record cannot be classified safely.

The recovery `openPreviewRequest` includes `initialTime` from the captured playhead. Candidate opening validates it against duration, pauses playback, and displays that exact moment. Ordinary candidate opening may omit `initialTime` to retain its existing behavior. This resumes the review position; it does not restore editor selection or undo history.

Online resume sessions with a valid reported active-rig topology include `checkpointDiscovery`, a ready filtered list request. Missing topology or offline state yields `null`; it does not guess a recovery target. This discovery uses heartbeat metadata only and still requires fresh inspection for restore preview. Successful candidate-open jobs also return `readbackHandoff`: read and poll the actual editor draft, confirm the expected recipe fingerprint, and compare `currentTime` with `requestedInitialTime` before describing recovery as reconciled.

For recovery, select the intended rig in Rig Library, inspect it freshly, and call `motion_editor_checkpoint_restore_preview` with the checkpoint ID and exact checkpoint fingerprint. A changed session or rig UUID after restart is allowed, but the recorded topology signature and driven authored joints must match. Different topology needs a separate reviewed retargeting workflow. The preview returns the exact recovery recipe and an `openPreviewRequest`; it does not queue a Studio mutation. Opening a candidate retains the existing dirty-draft guard. To replace an open draft, first read its current fingerprint and use the guarded, undoable editor-candidate apply workflow. Review the recovered animation before any approved save/export. If its old library parent is unavailable, the preview discloses that and omits parent lineage from the open request.

Author through the existing tools and preserve each output under its own filename. Call `motion_workflow_attach_candidate` with `workflowId`, `revision`, `artifactPath`, `changes`, and `evidence`. Each evidence item has an absolute `path`, `view`, `description`, and optional `time` in seconds.

- Models need at least two distinct views at each stage. Show bent poses as well as rest views during rigging review.
- Animation needs distinct explicit sample times at each stage. Include contacts and transition boundaries; still frames do not establish smooth playback on their own.
- VFX shape needs two views. Timing and integration need distinct explicit sample times.

Attach 2-12 distinct PNG or JPEG images, each no larger than 2 MB. The artifact can be at most 128 MB. These limits bound transport and local memory; they are not a game asset budget.

Animation workflows require `artifactPath` to be a valid Motion Tools animation recipe JSON. Its parsed recipe fingerprint is stored on the candidate and must match the saved animation fingerprint before technical test-run provenance can be linked. This prevents attaching an unrelated file or linking a different saved animation as if it were the staged candidate. It does not prove the screenshots depict that recipe; image-to-artifact identity remains a review limitation, so capture and inspect views from the exact evaluated candidate.

For the animation playbook, prefer `motion_workflow_attach_candidate_captures`: after retrieving and visually inspecting the Studio capture IDs, pass those IDs, their `sessionId`, and the exact recipe file. The server re-fetches and verifies each PNG and accepts only unsaved-candidate captures from the exact recipe fingerprint and one unchanged active rig, then stores the images and capture IDs in the workflow itself. This removes the manual PNG save/path step and makes the sample time/view and image hash auditable with the evidence. The tool still does not decide whether a pose is good; `motion_workflow_read_evidence` returns the image plus its verified capture binding for review. The path-based `motion_workflow_attach_candidate` remains available for model/VFX and manual-reference workflows, but its screenshots are not intrinsically bound to the artifact.

Native-capture candidates also carry `captureCoverage`: the expected and attached whole-body time/view pairs are assessed separately from focused close-ups. A close-up-only set reports `missing_whole_body`; missing required whole-body frames reports `partial`. In either state, an all-pass `motion_workflow_review` is rejected—the agent must capture the missing moments or use `unknown` for criteria the available evidence cannot support. Focused joint views are useful supporting evidence, but cannot replace whole-body review frames. `complete` means only that all scheduled whole-body stills were attached, not that motion is smooth or artistically successful.

An all-pass AI animation review has two additional evidence gates: every candidate image must have been returned through `motion_workflow_read_evidence` in the current MCP server process, and each attached image must be a complete Studio capture bound to the exact candidate recipe fingerprint. A server response receipt confirms only that the server constructed a response containing those image bytes; it cannot confirm client receipt, model perception, or correct interpretation. Manual screenshots may be references but cannot establish the exact candidate's rendered appearance. If capture or visual inspection is unavailable, record the affected criteria as `unknown`; user-authored review is not subject to the AI evidence gate.

Additionally, every passed animation requirement and exclusion in an AI review must cite whole-body captures at two or more distinct times from that exact candidate. A complete capture set elsewhere in the candidate is not a substitute for criterion-level citations, and focused close-ups are supplemental. This makes it auditable which time-separated frames support each pass; it still does not prove smooth interpolation between captured frames.

`motion_workflow_read` may offer `motion_workflow_append_candidate_captures` for a capture-bound, unreviewed animation candidate. Use the same unsaved recipe, active Studio session, rig, and topology. Append exact missing whole-body moments to recover incomplete required coverage, or append a supplemental whole-body moment/focused close-up when a material beat was omitted by the planner. Supplemental images stay on the same candidate but never expand the original candidate batch's required schedule or make missing planned coverage complete. The server preserves earlier evidence and verifies the recipe fingerprint, rig/session, topology, Studio capture metadata, image checksum, frame uniqueness, and animation duration. Reviewed candidates are immutable. This adds evidence only: it does not revise or save/export the animation, or assess its quality.

Call `motion_workflow_read_evidence` for each returned `evidenceId` to inspect it. To inspect a reference image, use its zero-based `referenceIndex` instead. Supply exactly one selector. Reference image delivery has the same 2 MB limit. Other reference file formats remain paths for the client's appropriate reading tools.

For an all-pass AI workflow review, the server requires every exact candidate image to have been returned through `motion_workflow_read_evidence` during the current server process. Candidate image responses include a receipt bound to the workflow revision, candidate ID, evidence ID, and image hash. This catches a review that advances without even requesting the image bytes; it does not prove the model perceived or interpreted them correctly. After an MCP server restart, retrieve the candidate images again. If the client cannot inspect image blocks, do not force a pass—record unsupported visual requirements as `unknown`.

For animation, an all-pass AI review additionally requires complete Studio captures bound to the exact unsaved candidate recipe fingerprint. Manually attached screenshots and reference images may still inform critique, but do not prove what the exact candidate looked like; use `unknown` for visual requirements when no fingerprint-bound capture is available. A user review is not subject to this AI evidence gate because the user may inspect the candidate directly.

For animation candidates, you can attach stronger technical provenance after the candidate has been saved as a Motion Tools animation and exercised by a persisted Studio acceptance run. First use the normal `motion_animation_test_plan_preview` → reviewed `motion_animation_test_plan_create` → `motion_animation_test_plan_run` flow. Then call `motion_workflow_attach_animation_test_run` with the workflow/candidate IDs, saved animation ID, exact plan ID and persisted run ID. The workflow checks that the immutable plan pins the current recipe, the run belongs to that exact plan revision, the selected animation passed, and the workflow candidate artifact is the exact recipe JSON. This records technical evidence and the rig topology; it does not auto-pass the creative review or substitute for a person inspecting the viewport.

Image bytes are returned to the connected MCP client. Its model provider may process those bytes under that client's settings. No separate provider request is made by Motion Tools.

## Review and revise

Call `motion_workflow_review` with the latest `candidateId`, current revision, and a review. Mark the reviewer `ai` for model judgments. Use `user` only to faithfully record feedback the user actually supplied.

Review every requirement once as `pass`, `fail`, `unknown`, or `not_applicable`. Each finding includes its reason and candidate evidence IDs. Failures need a concrete correction. An early-stage requirement can be not applicable with a reason, but final review must assess all requirements. Review every avoid item by its zero-based index as pass, fail or unknown, with evidence and a reason.

Do not mark timing as passing from a single flattering frame. Do not mark skin deformation as passing from a bone count. If the evidence is insufficient, use unknown and collect better evidence. A passed review advances one stage; any failure or unknown keeps the stage active. The final `reviewed` state describes the record, not a quality certification.

After three candidates in one stage, stop cosmetic retries and reconsider the approach. `motion_workflow_revise_brief` records revised instructions or construction choices and restarts the stages while preserving history. Do not use it to conceal failed attempts. Reference edits also require a new brief revision. A changed artifact or preview requires a new candidate under the appropriate brief revision.

For animation, author in this order: interpret intent and constraints; establish distinct anticipation/action/contact/recovery poses appropriate to the action; allocate timing and stagger related body parts; add only breakdowns needed for arcs, spacing, contact or transitions; then preview and polish. Make each beat readable through the silhouette, coordinate the hips/torso/shoulder with the acting hand or foot, and stagger trailing joints only when the action calls for it. Do not use a fixed pose count, force irrelevant phases, or treat declared contact as an IK lock. Before posing or queuing IK, call `motion_agent_readiness` with the active `sessionId`, `rigId`, required Studio features, and any semantic roles the action depends on. Exact standard-rig role mappings are ready; unique custom-name inferences remain unknown until explicitly reviewed, while ambiguous or unavailable roles block the preflight. For a rig-bound `motion_animation_blueprint_preview`, a pose can name a standard `semanticRole` such as `left_hand` instead of translating it to a rig-specific joint name; the tool resolves only exact recognized R6/R15 convention mappings and returns the mapping evidence. For custom rigs, use `motion_animation_resolve_rig_semantics` to inspect candidate joints, then author only the exact joint name after reviewing it; name-token inference alone is not anatomy. Resolver results now include the inspected root-to-joint chain, rest-basis quaternions, and segment-length estimates, plus explicit chain integrity and a cap on ambiguous candidate detail. Use this context to understand which joints influence the selected limb and compare candidates, not to assume anatomical axes or limits: the basis is a rest orientation and the size estimate is not visible geometry. Use the selected rig's driven names and parent hierarchy from `motion_studio_inspect`. Rig-bound provider generation requires the inspection identity, rig profile and topology signature to agree with the active Studio rig; Motion Tools rechecks that same rig before saving, so a changed selection or topology aborts the draft instead of attaching stale rig provenance. Inspection does not provide custom anatomical axes or limits, so confirm transforms on the target rig. `motion_animation_audit` reports structural advisories such as sparse tracks, synchronized timing and possible loop angular-velocity changes. For exact active-joint coverage, pass both `sessionId` and `rigId` from a fresh inspection; this reports matched/unresolved joint names, active authored channels, inactive layers, and driven joints without authored tracks. Missing channels are inspection cues, not failures, since deliberate stillness is valid. Without a fresh live inspection, coverage is omitted rather than guessed. Treat audit output as prompts to inspect, not an artistic score or automatic rejection. Unsaved candidate evaluation derives rig coverage from the exact live telemetry it samples and honors an explicitly supplied `jointMap`; every alternative in a candidate comparison reports its own coverage. Preview the whole clip and its important transitions in the Motion Tools viewport before saving.

In the Studio timeline, Shift-click keyframes to select or deselect a group, then drag any selected interior key to retime the group together. The editor preserves each selected key's spacing and uses one shared snapped offset across tracks; it clamps before unselected neighbors and never moves fixed start/end keys. Undo restores both the animation and its key selection. Use this for timing edits that should retain pose rhythm, then preview the full clip because changing key times changes interpolation and contact timing.

Copy one or more selected keys with Ctrl+C, move the playhead, and use Ctrl+V to paste the pose group. The active key is the timing anchor; all other selected keys keep their relative offsets, transforms, and outgoing easing. Paste is one undoable edit and selects the inserted group. It fails without changing the recipe if a destination track is missing, a key would collide, the group crosses a fixed clip endpoint, or a per-track/recipe key budget would be exceeded. Copy/paste matches destination tracks by exact joint name, so review the active layer and rig before pasting.

Mirror writes to the opposite-side joint at the selected key's exact time; if the target has no key there, the editor inserts one by sampling its prior curve before applying the mirrored pose. It no longer modifies a merely nearby key. Loop endpoint mirrors keep both endpoint transforms matched, and key limits are checked before insertion. The reflection crosses the rig-local X plane and converts through the source and target joints' measured rest orientations, which supports different custom-rig joint bases. Review the result in the viewport, especially for asymmetric rigs or rigs whose naming does not encode left/right convention.

### Iterating an animation without losing accepted work

When assembling an animation from saved poses, use `motion_pose_sequence_evaluate` for same-rig measurements, then preview the selected placements and open that exact recipe in the Motion Tools viewport. If AI visual judgment matters, the preview is not enough: run screenshot preflight, capture the exact recipe on the same rig, and inspect every returned PNG. If capture is unavailable or permission is not granted, leave rendered judgment to the user in the viewport. Apply only the exact preview fingerprint after the user chooses to proceed; technical samples and screenshots are evidence, not approval.

For a single saved pose, call `motion_pose_preview` first and inspect `rigCompatibility`, `jointCoverage`, `appliedJoints`, `skippedJoints`, and `createdTracks`. Compatibility is labeled `unknown` when the animation lacks verified source-rig provenance; do not treat matching joint names alone as proof of R6/R15 compatibility. Full-body snapshots are stricter: provide the active `sessionId` and `rigId`, and the snapshot topology signature must match the live Studio rig. Review newly created snapshot tracks carefully: their neutral clip-boundary keys mean a pose sampled mid-clip can introduce movement into joints that previously had no authored track. Pass those same rig identifiers and the exact preview fingerprint to `motion_pose_apply`; the server rechecks the candidate before saving.

`motion_snapshot_apply` is the same guarded commit path for full-body snapshots, not a preview bypass: obtain its `expectedCandidateFingerprint` from `motion_pose_preview` and pass the same session/rig and pose timing. A topology change or session switch invalidates the candidate.

Treat each preview fingerprint as a lease on one exact candidate, not as a reusable approval for later edits. For an unsaved blueprint, keep the original request and reviewed recipe, edit the blueprint deliberately, then call `motion_animation_blueprint_preview` again; its new fingerprint binds the complete input, resolved semantic roles, parent content and inspected rig profile. For a saved animation, use `motion_animation_patch` with `dryRun: true`, `includeAudit: true`, and explicit `preserve` regions for already accepted motion. Inspect the complete returned recipe, preservation report, affected targets and before/after local-motion diagnostics. If the candidate is good, repeat the identical source asset, ordered operations and preservation constraints with `dryRun: false` and the exact preview fingerprint; any change requires a fresh preview. Then evaluate the resulting revision on the same inspected rig and compare it against the previous accepted revision before describing it as improved. Numerical audit deltas only indicate what changed—they do not decide whether the change is artistically better. Never commit from stale viewport evidence, and never silently reinterpret a passed requirement; record new user intent through a brief revision when the creative target itself changes.

Playback priority is a runtime blending decision, not part of pose quality. Author it only when the user specifies the intended playback context; otherwise leave the optional recipe field unset for the game to decide.

For looping clips, inspect both pose and velocity continuity. Audit `loopSeamVelocity` now includes `endpointPositionOffsetStuds`, shortest-arc `endpointAngularOffsetDegrees`, and the actual `velocitySampleStepSeconds` alongside velocity discontinuities. A constant-speed channel can have zero velocity discontinuity yet jump from a different endpoint pose at wrap. These are separate local-channel measurements before layer composition and hierarchy; root travel/turning can be intentional, and inactive layer deltas do not establish visible motion. Use them to choose boundary captures, then review the rendered loop without inventing acceptance thresholds.

Use `composedLoopSeam` for the resultant local joint boundary after enabled weighted layers and root-motion composition. It reports the same pose/velocity quantities, excludes joints authored only in inactive layers, and preserves individual-channel diagnostics separately. Opposing additive channels can cancel their endpoint offset; partially weighted cancellation can leave a residual. The result still excludes rig hierarchy and world-space contacts, so rendered review remains necessary.

Explicit acceptance criteria can now include `maxLoopComposedPositionOffsetStuds` and `maxLoopComposedAngularOffsetDegrees` (0–180). Both require `loop: true` and use the worst resultant local joint endpoint offset. They are caller-selected limits; suggestions never invent them. Test-plan previews expose both check IDs and pin the criteria with the plan fingerprint; comparison treats a changed limit as changed criteria. Missing composed evidence yields unknown. Intentional root accumulation contributes to these measurements, so choose limits consistent with the requested cycle.

For selective checks, pass `jointLoopLimits` with 1–32 unique exact authored joint names and at least one `maxPositionOffsetStuds` or `maxAngularOffsetDegrees` per joint. Limits apply to composed local endpoints only for those joints; unlisted joints receive no inferred requirements. This supports a traveling root with separately constrained head/limb loops. Missing, inactive-only or differently cased joint evidence is unknown, not zero. Duplicate names ignoring case and non-looping contracts are rejected. These optional criteria persist with the plan and appear as `loop-joint:<joint>:position`/`angular` offline checks; changed limits count as changed criteria. They do not prove foot contact or world-space stationarity.

Blueprints can author ordinary in-action cues with `events: [{ name, phaseId, progress, value? }]`. `progress` is normalized within the referenced phase (0–1); each event compiles to a native recipe marker with `phase: "event"`, so names such as `Impact`, `Release`, and `FootPlant` remain event cues instead of becoming action-phase boundaries. The compiler validates referenced phase IDs and the 100-marker total recipe limit. This adds timing metadata only; it does not create contact, collision, or gameplay behavior.

Preview readback includes each event’s authored phase ID and progress plus resolved clip time, sorted deterministically by time and identity. Equivalent blueprints with events supplied in a different array order therefore compile to the same marker ordering.

Contact readback likewise includes the authored `phaseId`, normalized `startProgress`/`endProgress`, and compiled clip-time `start`/`end`. Contact summaries and recipe windows are sorted by compiled interval and identity, making equivalent reordered declarations stable. Contacts remain metadata declarations, not proof of a held contact or an IK solve.

Blueprint commit persists phase intent, phase-local events, and phase-local contact declarations in the asset’s validated `authoringIntent` metadata, bound to the exact source recipe and an independent content fingerprint. Reads validate the metadata fingerprint; new metadata must name the exact recipe being saved. Existing phase-only records without the optional content fingerprint remain readable. AI visual-review capture tools expose the shared `authoringIntentTimingRelation`: `exact_current_recipe` means the intent's source fingerprint matches the captured recipe, `historical_reference` means it does not, and `unavailable` means the caller supplied no reference intent. The additional `intentRelationToCapture` distinguishes `exact_capture_source` from `reference_recipe_only` (intent matches the selected asset but not the capture) and `historical_only` (intent matches neither). Intent is always reference context, never visual evidence; do not apply stale phase/event/contact times as current candidate timing.

AI critique receives the same stale-timing distinction. It may preserve the creative intent as context when consistent with the user's brief and fresh evidence, but phase/event/contact coordinates from a stale authoring intent must never be reused as timestamps for the current recipe.

Authoring-intent timing uses the shared `authoringIntentTimingRelation` classification across save, review, and editor-read results: `exact_current_recipe` means the intent fingerprint matches the compared recipe, `historical_reference` means it does not, and `unavailable` means intent or a comparison fingerprint is absent. Reading an open editor draft also returns inherited `editorAuthoringIntent` when its source asset carries blueprint intent. Its editor-specific `timingRelation` is `exact_current_draft` only when the intent's source recipe fingerprint equals the exact current draft; `loaded_source_only` means it matches the loaded source but the draft has since changed; otherwise it is `historical_only`. Only the exact-current-draft relation permits using phase/event/contact coordinates as current draft times. The metadata is read-only and does not affect the draft, save, or export state.

## Current limits

The staged workflow is an orchestration and evidence ledger: it checks artifact fingerprints, review coverage, evidence references, revision conflicts and stage transitions, but it does not automatically run the separate authoring, preview or capture tools for you. Motion Tools has separate Studio tools for candidate capture and animation comparison; native screenshot support is experimental and must pass a live capture preflight in the current Studio installation. A successful capture or comparison is evidence for review, not an automatic quality verdict.

For screenshots attached through `motion_workflow_attach_candidate_captures`, Studio provenance binds PNG bytes, candidate recipe fingerprint, session, rig topology, view, and sample time; manually attached files do not carry that proof. Neither route verifies that an AI reviewer judged the visible evidence correctly. The workflow does not generate or edit assets itself, simulate cloth or gameplay physics, enforce actions in a separate Blender MCP, or prevent a client from bypassing the workflow with low-level tools. For animation, use candidate comparison tools when appropriate, then have a person review the actual motion and decide whether to save or accept it. Model and VFX appearance still require human review of representative rendered evidence.
