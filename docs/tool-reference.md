# Tool reference

Animation acceptance schemas support optional `jointLoopLimits: [{ joint, maxPositionOffsetStuds?, maxAngularOffsetDegrees? }]` for 1–32 unique exact authored joint names. Each entry needs at least one caller-defined limit and the case must declare `loop: true`. Evaluation uses composed local endpoint offsets; missing joint evidence is unknown. Test-plan previews, persistence and comparisons retain these criteria. Unlisted joints, including an intentionally traveling root, receive no inferred limit. Global `maxLoopComposedPositionOffsetStuds`/`maxLoopComposedAngularOffsetDegrees` remain available for worst-joint checks.

`motion_studio_open_candidate` accepts optional `initialTime` in seconds, bounded by the candidate duration. When supplied it opens paused at that pose. Checkpoint recovery includes the captured playhead automatically in its explicit open request. The recipe fingerprint remains a content identity; preview time is separate UI state and does not change animation content or overwrite protection.

Checkpoint discovery filters: `motion_editor_checkpoint_list` accepts optional `rigSignature`, captured `rigId`, and `dirty` together with `offset`/`limit`. All supplied filters must match; pagination and `total` apply to verified matches. After a reconnect changes rig IDs, use the freshly inspected topology signature to find candidates. Summary `sourceRigName` is source lineage, while `rigId` and `rigSignature` identify the captured draft. Corrupt-record diagnostics remain store-wide. Matching topology does not bypass `motion_editor_checkpoint_restore_preview` or authorize overwriting an open draft.

Editor recovery: `motion_editor_checkpoint_create` stores only a succeeded Studio editor-read snapshot, bound to `sessionId`, `rigId`, `readJobId`, and `expectedDraftFingerprint`; optional `name`/`note` label it. Poll `motion_studio_job` after `motion_studio_read_editor_draft` and use its `checkpointHandoff`. The snapshot is historical and immutable, and identical retries do not duplicate it. `motion_editor_checkpoint_list` returns paginated compact metadata and corrupt-record diagnostics; `motion_editor_checkpoint_read` verifies the full record and exact recipe. These local recovery files are separate from animation library revisions. `motion_editor_checkpoint_restore_preview` requires `checkpointId`, `expectedCheckpointFingerprint`, and a freshly inspected explicit target `sessionId`/`rigId`; it blocks topology mismatches or undriven authored channels and returns a non-mutating recovery plan. Existing open-candidate and editor-apply protections still prevent overwriting newer unsaved work. `motion_agent_resume.editorCheckpoints` surfaces recent recoverable snapshots after reconnect (`checkpointLimit` defaults to 5, maximum 20). No checkpoint tool publishes, exports, or automatically restores the viewport.

Build identity: the packager creates deterministic `dist/build-identity.json` from all compiled server modules, the dependency lock, and the Studio source bundle. The plugin embeds its source fingerprint before pairing, and heartbeat `motionToolsBuild` reports it. The server captures its manifest once at module startup and reports it in authenticated `/health`, `motion_capabilities`, and `motion_agent_resume`; rebuilding files cannot relabel that already-running process. Resume exposes `serverBuildAssessment` and each session’s `pluginBuildAssessment` as `current`, `different`, or `unknown`. Offline, missing, malformed, and legacy identities are unknown. Different builds produce reload/update guidance without retrying a job or altering a draft. The doctor additionally verifies the manifest against current artifacts and can compare bridge health identity; a healthy legacy bridge can therefore have an unknown `bridge_build` check. These are reported build identities, not authentication signatures, verification of runtime modifications, or visual/animation quality verdicts.

`motion_installation_diagnostics` is a read-only setup doctor. It compares current Studio source with the generated, paired, and installed local plugin, checks existing pairing and prepared MCP paths, and reports online sessions in this server. `checkBridge: true` additionally requests authenticated localhost health with a 1.5-second timeout, a 4 KiB response limit, and no redirects. It does not disclose pairing tokens, create settings, repair files, install a plugin, launch another server, or change a draft. Source/configuration problems return actionable `needs_attention` checks; unavailable verification returns `unknown`. A file match or healthy bridge does not establish what code an already-open Studio/client loaded. Use `motion_agent_resume` and `motion_agent_readiness` to continue the live animation workflow. The CLI equivalent is `npm.cmd run doctor -- --json`; exit codes are 0 for ready, 1 for required repairs, and 2 for incomplete verification.

For custom-rig semantic-role poses in `motion_animation_blueprint_preview` or `motion_animation_blueprint_goal_preview`, inspect the rig and role-resolution evidence, then pass `semanticRoleMap` with the reviewed exact driven-joint name for each requested role. The server rejects non-driven, duplicate, unused, or standard-rig-overriding mappings and includes the resolved user-attested map in the preview fingerprint. This is not anatomical verification.

### Evaluate an unsaved AI-authored animation

When the connected coding agent has built a full animation recipe, call `motion_animation_candidate_evaluate` before `motion_library_save`. It samples that exact recipe on the selected Motion Tools rig and returns a content fingerprint. For a retargeted candidate, also pass `retargetPreview` with the exact original retarget inputs and `expectedCandidateFingerprint`; the server recomputes the preview, rejects stale fingerprints or recipe mismatch before sampling, and verifies the target profile ID/signature matches the live evaluation rig. `retargetPreviewEvidence` records the verified source/candidate fingerprints and target topology. This closes the retarget-preview → live-evaluation binding; it still does not imply visual approval. The evaluator returns a content fingerprint, structural audit, Studio pose inspection, rig-signature-bound joint coverage, exact-name `viewportReadiness`, and (if supplied) caller-authored mechanical acceptance results. The viewport has a strict exact-name gate: do not open or describe it as reviewed unless `viewportReadiness.status` is `ready`. If the explicit `jointMap` covers every authored channel, the agent may still request temporary screenshot capture to inspect a name-mapped pose; the capture metadata reports its mapping fingerprint and renamed-joint count. Such a preview is not a true retarget: the map does not convert local axes, solve IK, or prove semantic equivalence. Use the rig-profile retarget workflow for that. A bounded `reviewFocus` surfaces structural advisories, up to eight observed local-motion extrema round-robin across available signal types (preserving each signal's within-type rank and time/joint/phase/patch context), and only failed or unknown caller-declared checks. Values with different units are not globally comparable. It also explicitly reports whether criteria were provided, their aggregate status/summary, or `not_requested`; an empty unresolved-check list must never be mistaken for passing checks when no criteria were supplied. These extrema are inspection cues, not defects or quality rankings; full reports remain available. The agent can use the findings to revise its in-memory recipe and evaluate it again; none of these calls create library assets. Pass acceptance requirements only when the project/user has stated them—missing Studio evidence is never a pass. This workflow is AI-provider agnostic: Motion Tools evaluates the main agent's candidate rather than invoking another model. It still cannot establish artistic quality, rendered mesh appearance, collision/physics behavior, or user approval; save and review the exact candidate only after deciding it is ready.

Rig coverage includes the dedicated `rootMotion` channel alongside base tracks and layers. It reports the channel under its mapped driven joint, while counting that joint only once; a top-level `rigCoverage.rootMotion` summary also gives its source joint, mapped joint, key count, and `resolved`/`unresolved` rig status.

Candidate evaluation also returns `spatialTrajectoryEvidence` for up to 12 prioritized joints (root motion, declared contact effectors, then authored joints). Each trajectory includes its parent/driven metadata, start/end, net displacement, path length, bounds, maximum sampled speed, and up to 24 time-labeled positions; exact `sampleCount`, omitted trace count, and maximum sample gap disclose temporal coverage. If requested joints exceed the detail cap, `omittedJoints` names up to 24 omitted entries with both requested and resolved joint names, while `omittedJointListTruncatedCount` reveals any further omissions. `orientationFrame` is `rig_pivot_composed`: orientations are evaluated object orientations in the rig-pivot frame, include ancestor motion, and are not authored local Euler channel values. When every sample has an orientation, `traceSelection.orientationEvidence` gives the reference sample, largest sampled angular drift in degrees, peak angular speed in degrees per second, and exact sample IDs for both events. When a captured rig rest pose is also available, it separately gives the sample and degrees of the largest deviation from rest; otherwise that field is `null`. Selected trace points include their sampled quaternions. Missing orientation telemetry yields `null` rather than a fabricated zero. Current Studio telemetry supplies hierarchy-composed joint-pivot or node-pivot positions relative to the rig pivot. Older telemetry without those fields is explicitly labeled ground-relative. Neither form is literal world coordinates, continuous motion, rendered/skinned geometry, gameplay displacement, or proof of contact; use permission-gated captures and inspect the actual images for visible judgments.

When available, each trajectory also includes the exact rig driver class in `targetKind` (`Motor6D`, `AnimationConstraint`, or `Bone`), alongside the same parent/driven context supplied to rig-bound blueprint joint guides. Older telemetry may omit this field. Driver class identifies the controlling Roblox object; it does not establish local axes, anatomy, joint limits, or skinning.

`declaredContactEvidence` groups the same Studio samples by each recipe contact window. It exposes start/midpoint/end coverage, sample gaps, first-observed drift, cumulative travel, peak segment speed, available orientation drift, and a bounded time-labeled trace. `pointSource`/`coordinateFrame` distinguish current rig-pivot-space joint/node pivots from legacy ground-relative telemetry. Missing joints and windows with fewer than two samples remain explicit; the measurements never invent acceptable thresholds or claim a pass. Drift is measured from the first observed in-window sample, which may be later than the declared start if its boundary is unsampled. Stable pivots do not prove physical contact or visible correctness.

Live pose, contact, root-motion, and acceptance lookups prefer exact case-sensitive joint names. A case-insensitive fallback is used only if it resolves to one sampled rig node; ambiguous matches are reported as unknown/failed evidence rather than measurements against an arbitrary joint. The supplied `jointMap` is applied before this check.

If the main agent has authored multiple complete options, call `motion_animation_candidates_evaluate` with 2–3 `{id, recipe}` entries. Every distinct fingerprint is sampled in order on the same rig. The first recipe is a comparison baseline only; each option receives its own `reviewFocus`, rig coverage, viewport readiness, audit/inspection and optional explicit acceptance results, while later options also receive normalized-progress trajectory and declared-contact comparisons against the baseline. Duplicate recipes reuse one Studio sample. If any candidate is not viewport-ready, resolve its exact joint names before attempting matched rendered capture. Compare the evidence with the stated creative intent; the tool deliberately does not assign a winner or write library assets.

Trajectory comparisons pair rig nodes by exact, case-sensitive names and parent hierarchy. A case-only node-name difference is treated as a topology mismatch, not normalized into a potentially incorrect comparison.

### Preflight a Roblox animation export

Before adding a new draft to the library, `motion_studio_validate_animation_candidate` can run the same conversion directly from an inline recipe. It returns a Studio job and uses the exact `Authoring.sequence` converter with rig/topology checks and frame/pose/marker counts. Its synthetic candidate identity is ephemeral: successful conversion does not create the 10-minute save capability and cannot authorize `motion_studio_save_animation`. If chosen, save the exact candidate to the library, then run the saved-asset preflight below to receive a capability bound to the real asset ID.

Before saving a substantial animation, call `motion_studio_validate_animation_export` with the selected `sessionId`, `rigId`, and `assetId`. It converts the exact recipe through the same `Authoring.sequence` path used by save, then destroys the temporary `KeyframeSequence` without parenting or recording an undo. The result reports the recipe fingerprint, rig topology signature, frame count after nonlinear-easing baking, generated pose count, marker count, and a sorted, deduplicated `mappedTargetJoints` list. Studio also verifies that every listed target appears as a Pose in every generated keyframe. The list includes names from base tracks, every layer (even disabled/zero-weight layers), and root motion; it describes authored mapped coverage, not active motion or quality. The server verifies it against the exact recipe and joint map. This catches missing/mismapped rig joints and the plugin's 2048 baked-keyframe cap before a persistent save. After the successful job is read, the server returns a 10-minute `preflightFingerprint` capability bound to that session, rig topology, recipe revision, joint map, and conversion counts. It does not publish, upload, simulate gameplay, or judge animation quality.

For a release set, `motion_studio_validate_animation_export_batch` converts 2–8 saved clips sequentially on the same active rig and returns a fingerprint-bound valid/invalid result for every clip. Each valid clip includes its own sorted `mappedTargetJoints`; each temporary sequence is destroyed, and a failed conversion is reported per clip so the remaining candidates are still checked. The batch is deliberately non-authorizing: when you decide to export a specific valid clip, run its individual preflight to obtain that clip's save capability. Any active-rig or topology change invalidates the batch response.

Pass `assetFingerprint` as both `expectedFingerprint` and `userApprovedFingerprint`, plus `preflightFingerprint` as `expectedPreflightFingerprint`, to `motion_studio_save_animation` with the same rig, session, and joint map. Only provide `userApprovedFingerprint` after the user explicitly approves that exact recipe fingerprint. It is a caller attestation, not authenticated identity; neither a successful preflight nor permission to call the tool counts as approval. The save rejects mismatched approval/export fingerprints and verifies the same selected rig topology again in Studio. One preflight authorizes one save job; repeating the same request returns that existing job. The deterministic preflight identity is also stored on the KeyframeSequence, so after a server restart a new preflight of the same export finds and reuses the existing object instead of duplicating it. Studio work remains queued until `motion_studio_job` reports success; a successful local save is a KeyframeSequence in the rig's AnimSaves location, not a published animation asset.

If a save job is `unknown`, or its MCP server lost job history, call `motion_studio_find_animation_export` with the current session/rig, asset ID, and exact asset/preflight fingerprints. It only searches an existing linked `AnimSaves` folder and returns `saved`, `not_found`, `duplicate_identity`, `identity_conflict`, or `related_candidates`; it never creates the folder or changes sequences. ### Search by motion shape

Beyond pose shape, each match reports declared-event timing separately: marker alignment pairs exact name/value/phase identities by normalized time, while contact alignment pairs exact effector/kind intervals by normalized interval intersection-over-union. `eventAlignmentPercent` combines them using the larger per-clip count per event class as weights; marker/contact subtotals and source counts remain visible. A missing event class is `null`, not 100%. These are declared timing/identity comparisons—not action semantics, proof of physical contact, or part of the local-pose shape score.

For cross-rig comparisons, `retargetedJointCoverageFraction` covers only active joints contributing to the current composed-pose score; `retargetedAuthoredJointCoverageFraction` covers every authored joint. Partial mapping can omit an unmapped disabled/zero-weight layer from the temporary comparison recipe; its name remains in `unmappedCandidateJoints`, but it does not lower evidence quality for the current composed motion. The full authored-coverage fraction and skip list preserve that warning for later layer activation or reuse.

`motion_animation_search_similar` compares one saved animation against a bounded set of the newest animation-library entries. Each match adds `evidenceQuality` (`strong`, `limited`, or `weak`) plus stable `evidenceLimitations` codes. This is an explainable evidence grade, not a probability or artistic-quality rating: weak means joint coverage is below 50% or mapping failed; limited means an evidence caveat exists; strong means none of the reported mechanical caveats apply. Codes identify incomplete joint/retarget coverage, name-only mapping fallback, missing rig provenance, omitted compared pose-key samples, and omitted event samples. A strong grade still does not imply semantic equivalence or visual quality. Shape coverage includes only joints with contributing base/root-motion channels or enabled, nonzero-weight layers; disabled and zero-weight layer-only joints do not lower the similarity score. Retargeting attempts every authored channel, including inactive layers, but a partial map may skip unmapped channels; the result reports these in `unmappedCandidateJoints` and separates them into `unmappedActiveCandidateJoints` and `unmappedInactiveCandidateJoints` with bounded omitted counts; null means the category was not assessed, while an empty list means it was assessed with no unmapped joints. `retargetedJointCoverageFraction` measures active composed-pose joints, while `retargetedAuthoredJointCoverageFraction` measures all authored joints. An unmapped inactive-only channel remains visible in the authored coverage and skip list but does not lower the current composed-pose evidence grade. When active channels are unmapped or cross-rig mapping fails, `mappingNextStep` tells the agent to use `motion_animation_suggest_joint_map`, treat the score as provisional/name-only as applicable, and preview on the target rig before reuse. It retains 33 uniform normalized-progress points and adds compared pose-key, marker, and contact-boundary times from both clips, up to 129 points total. If more authored times exist, it selects a deterministic stratified subset, prioritizing compared pose-key times before marker/contact event times. Each result reports total and per-category authored-time counts, so an AI can distinguish omitted contributing pose keys from omitted event times. Squared errors are integrated with normalized-progress trapezoidal weights, so dense key regions do not receive more influence merely because they contain more keys. The candidate ranking composes base tracks, enabled weighted layers in stack order, and matching root-motion tracks. Joint lists, tied candidate rankings and mapping diagnostics use stable ordinal ordering, so equivalent recipes return reproducible result ordering regardless of input ordering or machine locale. If both query and candidate have saved rig profiles with different signatures, it uses the conservative joint-map advisor and retargets a candidate with strong one-to-one mappings into the query rig basis before comparing; the result states the `comparisonMode`, mapped pairs, skipped joints, and mapping warnings. If provenance or a sufficiently strong map is missing, it uses exact joint names and reports that fallback instead of pretending cross-rig alignment succeeded. The normalized score uses a fixed 4-stud translation scale and 180-degree rotation scale, and treats missing query joints as maximal normalized error. Results also expose matched-joint coverage, query-only/candidate-only joints, unnormalized translation and rotation RMSE, source rig type when known, and duration ratio/difference. Duration is deliberately not folded into the shape score, so the agent can distinguish similar motion performed at a different speed. Set `rigType` to filter candidates with known matching provenance; candidates with unknown provenance are omitted by that filter. `scanLimit` caps how many recent animations are compared and `scanTruncated` tells whether older entries were left out. Optionally pass both `sessionId` and `targetRigId` to use the currently selected, recently inspected rig. If omitted, the top-level `targetRigNextStep` points to `motion_studio_sessions` and explains how to use the Motion Tools Rig Library selection before rerunning search. With a fresh target rig it also returns `retargetHandoff`: a ready-to-call read-only retarget-preview request only for complete strong mappings, a mapping-advisor request for partial/weak mappings, or an explicit source-provenance-required state. This request is advisory data; the search never runs the preview or commits a retarget automatically. No map is applied automatically, and the advisor is not proof of local-axis, skinning or rendered suitability. Similarity remains numerical local-pose retrieval, not semantic action recognition or world-space motion comparison. Inspect and preview a candidate on the intended rig before reusing it.

### Compile a rig-mapped locomotion gait

Use `motion_animation_gait_preview` to generate a deterministic in-place `walk`, `run`, or `sneak` cycle. For proportions, choose either `strideDegrees` (the total forward-to-back hip arc) or `strideReachRatio` (the desired one-sided horizontal reach as a fraction of hip-to-foot chain length); do not pass both. The ratio is converted to a hip angle with `2 × asin(ratio)`. If an inspected target profile or a parent animation's profile is available, the response reports left/right leg-chain lengths and estimated reach in studs from the profile's segment lengths. The chain follows exact mapped joint parent links, and a broken chain with an explicit ratio fails rather than guessing. Without a profile the ratio still determines a dimensionless pose, but stud-space reach is returned as unknown. The estimate sums part-center distances; it is not a world-space foot trajectory or collision measurement.

The compiler samples each complete cycle, writes exact matching loop endpoints, and emits support intervals plus uniquely named plant/lift markers. `cycles` is 1–7; `samplesPerCycle` is 8–24 and the product may not exceed 127 samples so each track remains under the 128-key limit. Maximum 30 seconds and the animation recipe's aggregate track/key/contact/marker caps still apply. Supplying both `sessionId` and `rigId` requires a fresh successful inspection of that active rig; every mapped joint must be reported as driven. `parentAssetId` creates an immutable child revision and binds the preview to parent content. Review the complete returned recipe, diagnostics and candidate fingerprint; commit only the exact same request with `motion_animation_gait_commit` and its `expectedCandidateFingerprint`. Repeating a matching commit is idempotent.

This is an editable in-place gait scaffold, not motion capture or a learned animation. It authors no root travel and performs no IK, ground collision, foot locking or anatomy inference. Support intervals express author intent, and local axis/amplitude choices must be checked in Studio. After committing, evaluate the saved clip on the intended rig, preview it in the Motion Tools viewport, and visually inspect seam, stride direction, knee bend, foot plant, and arm timing before exporting a Roblox asset.

### Audit animation motion

For a recipe that has not been saved to the Motion Tools library, call `motion_animation_audit_recipe` with the complete current recipe. It runs the same read-only easing-aware audit without saving or requiring Studio and returns `saved: false` plus a `candidateFingerprint` bound to the parsed recipe. Its `next` handoff tells the caller to pass that fingerprint as `expectedFingerprint` to `motion_animation_candidate_evaluate`, verify the returned fingerprint, and then use that exact recipe and evaluator fingerprint in `motion_studio_open_candidate`. Any edit requires a fresh audit and evaluation. The result cannot establish rig compatibility, rendered appearance, artistic quality, or save approval. Use `motion_animation_audit` for an already-saved asset, optionally with a fresh `sessionId` and `rigId` to add rig coverage.


AI refinement targeting is segment- and phase-aware: `refinementPlan` computes speed, acceleration, and jerk peaks independently for every authored key segment, retains each signal's global peak, then favors the strongest candidates from distinct actual phase windows before filling any remaining slots. Phase identity is the concrete window, not merely a repeated per-label occurrence number. Every target includes phase/boundary context and any declared support/grip window covering the event time. These annotations improve review coverage but do not classify spikes as defects or prove physical contact.

Animation marker recipes may include `phase: "anticipation" | "main_action" | "follow_through" | "recovery" | "event"`. Explicit phase metadata overrides name inference; `phase: "event"` keeps gameplay markers named `Impact`, `Release`, `Cast`, etc. from creating false phase boundaries. Untagged legacy markers keep name-based inference. Blueprint markers are tagged automatically. This `phase` field is Motion Tools-only and is not serialized into native Roblox `KeyframeMarker` objects, so it must not carry game logic; exported markers retain their authored name, value and time.

`motion_animation_audit` returns structural advisories, `trackMotion`, `curveMotion`, `loopSeamVelocity`, `phaseTiming`, `coordination`, `actionPhaseMap`, and a compact `refinementPlan`. It analyzes base tracks, every pose-layer track (including disabled layers), and root motion; layer entries include ID/name, enabled state, blend mode and weight. `trackMotion` reports key-to-key speed and velocity-change metrics with key indices. `curveMotion` evaluates each track using its actual easing and shortest-path quaternion interpolation at the requested `sampleRateHz` (30, 60, 120 or 240; default 60), with every authored key time included. It reports peak local position/angular speed, acceleration and jerk with timestamps, evaluation count, and exact zero-based key-segment context including the outgoing easing. Sampling is bounded per channel by animation duration and key limits. For loops, `loopSeamVelocity` estimates incoming/outgoing position and angular velocities at matched small offsets from the boundary and reports the discontinuity by authored channel. `phaseTiming` marks onset, peak, last-active time and active coverage when speed is at least 5% of that channel’s peak; this relative threshold creates a useful timing envelope, not a physical event/contact boundary. `coordination` compares base-track local channels only. It groups peak times within one sample interval and returns up to 16 largest onset lags and 16 largest peak lags separately for position and angular motion, including each pair’s active-window overlap. This reveals timing relationships such as near-synchrony or stagger, but cannot say whether a relationship is intentional, compose layers, or infer hierarchy/world motion. `actionPhaseMap` segments the timeline only on markers with recognized phase names: anticipation/windup/preparation, action/attack/strike/impact/release/cast, follow-through, and recovery/settle/return. Ordinary event markers such as footsteps are not phase boundaries. Without a recognized marker it reports the whole clip as `unsegmented` and does not infer intent from peaks. Each interval includes start/end marker names, recognized boundary labels, active-channel summary, phase-local segment peak events, intersecting contact windows, and explicit detail-omission counts. Its `poseProgression` reports composed per-joint local entry/exit transforms, net translation/rotation, and peak excursion from the phase-entry pose; enabled weighted layers are composed in stack order and matching root-motion tracks are included. Uniform phase samples follow `sampleRateHz` with a 256-interval cap, and authored key times are sampled too. This is not a world-space hierarchy solve, rendered-silhouette judgment, or contact/quality verdict. `phaseDetailLimit` (1–16, default 6) bounds the listed active channels, position/angular peak events per phase, and pose-progression joints; total counts and omitted counts remain available. Conflicting labels at the same boundary remain `unclassified`; endpoint marker names are retained. Add named markers when you want the agent to analyze phase-specific timing. `refinementPlan` returns up to three highest measured segments for each of six signals (18 targets maximum), with the channel/layer, exact segment and event time, interpretation scope, and operation-specific repair guidance. Each signal is ranked from per-key-segment extrema, so a local acceleration or jerk peak is not hidden by another segment's global peak. Candidates prefer distinct concrete phase windows—including repeated windows with the same label—before filling remaining slots. Every target also provides `measurementProvenance`: sample rate, derivative order, and exact time stencil used for that estimate. If the stencil crosses an authored key or phase boundary, the report names the boundary and adjacent key-segment indices; `keySegment`/`patchFocus` still use a deterministic segment containing the event time, not a claim that the boundary change belongs to only that side. Review both adjacent segments before patching boundary-crossing estimates. A target explicitly remains `unclassified` until the agent visually decides whether it matters; numeric peaks are not presumed defects. Each repair option states when it is appropriate and its principal risk. Guidance prefers a dry-run easing change when endpoints are right, reserves a custom curve for deliberate timing shapes, and inserts a breakdown only for a specific missing pose. Root-motion targets call out that replacement affects the whole channel. Preserve contacts and accepted motion, compare before/after, then re-audit and preview; the tool never applies edits. It is a review-priority map, not a quality score. Derivatives are finite-difference estimates: discontinuities and extrema between samples may be approximated, especially at lower rates. These reports do not include rig physics, skinning or rendered appearance. Preview on the target rig before changing the motion.

### Run an offline animation benchmark

`motion_animation_benchmark` accepts a versioned JSON suite and runs without a connected Studio session. The shape is `{schemaVersion:1,cases:[{id,name,recipe,expectations:[{id,description,outcome,evidence}],limits?:{maxLoopSeamPositionVelocityDiscontinuityStudsPerSecond?,maxLoopSeamAngularVelocityDiscontinuityDegreesPerSecond?}}]}`; `outcome` must be `pass`, `warn`, or `fail`. Loop-seam limits require a valid `loop: true` recipe and are caller-authored thresholds in the range 0–100000. Recipe and contact-channel findings use deterministic IDs (for example `recipe-valid` and `contact-track:LeftFoot:0.2:1.8`) so a suite can assert explicit regressions. The report includes stable SHA-256 recipe, suite and report fingerprints, measured recipe counts, findings with evidence, expectation matches, case totals and limitations. Input is bounded to 100 cases, 100 expectations per case and 8 MiB. A missing expected finding is `warn`; an expectation mismatch fails the case. Case status measures conformance to expected findings, so a known failure explicitly expected as `fail` can match; unexpected failures or mismatches fail the case. The optional release gate defaults to blocking warnings and requiring at least one explicit expectation per case. Its fingerprint binds the exact report, resolved policy and decision. A passing assertion only means the declared recipe-level check matched. It does not validate world-space contacts, rig axes/hierarchy, rendering, artistic intent, skin deformation, physics or native Studio behavior. Seam values are matched one-sided finite-difference estimates on authored channels; they are not composed or rendered playback measurements. Keep the rendered front/side evaluation pilot separate; this offline tool does not complete that benchmark.

For durable run history, call `motion_animation_benchmark_record` with the suite and optional release-gate policy. Runs are append-only under `artifacts/animation-benchmark-runs`; their exact input suites are deduplicated in a content-addressed `suites/` archive. Use `motion_animation_benchmark_history` to list/filter, `motion_animation_benchmark_read` to verify and retrieve a run, and `motion_animation_benchmark_suite_read` to replay-verify and page through the exact source cases. `motion_animation_benchmark_rerun` reproduces the suite with its original gate policy without copying input back through the agent; it creates a fresh run record. `motion_animation_benchmark_compare` compares case status, recipe fingerprints, individual deterministic findings, and declared expectations. The comparison identifies findings that appeared/disappeared or changed severity/evidence; expectation changes distinguish a changed criterion from a changed observed result or match state. Case renames are surfaced while stable case IDs still align. It marks whether suite fingerprints match; changed-suite comparisons are exploratory. These are structural deltas only, not artistic-quality claims. Persisted reports and archived suites are fingerprint-checked before use.

### Compare animation revisions on a live rig

### Define animation acceptance tests

Use `motion_animation_contact_contract_build` to create a contact-regression template from an existing baseline animation. Supply the declared effector/window and an explicit `allowedDriftIncreaseStuds` margin; optionally supply `allowedTravelIncreaseStuds` and `allowedStepSpeedIncreaseStudsPerSecond`. The tool samples the current animation on the selected Studio rig and returns measured values plus exactly those margins as limits, the baseline recipe fingerprint and rig signature, and (for speed) structured worst-segment evidence. Missing, ambiguous, or sparse evidence aborts the build rather than inventing a limit. This preserves the baseline—it does not certify it as good. To test a new child revision, replace the template's `assetId` and pin that asset in a new immutable test plan after reviewing it.

The contact evidence-density gate measures the largest gap across the entire declared interval, including from its start to the first sample and from the last sample to its end. Missing boundary coverage is `unknown`, not a pass based only on dense interior samples.

Each contact requirement may also set `maxAngularDriftDegrees` (0–360). Studio compares each sampled world orientation to the first contact sample; missing orientation telemetry yields `unknown`. Position and angular limits are separate checks. Neither measurement proves floor contact, collision, or a correctly gripped prop.

To detect contact sliding beyond net drift, set `maxCumulativeTravelStuds` to bound the sum of displacement across consecutive sampled poses, and/or `maxStepSpeedStudsPerSecond` to cap the fastest adjacent-pose displacement divided by its sample interval. The speed check returns a structured `segment` with start/end times, both sample IDs, and displacement, in addition to its human-readable detail. Persisted plan runs retain this evidence, and plan comparisons expose both `baselineSegment` and `candidateSegment` when available. Cumulative travel is a sampled path-length estimate and, like all sampled checks, can miss movement between poses; keep `maxSampleGapSeconds` appropriately small. These limits are optional and appear as separate regression criteria in persisted test plans.

Support-foot checks may set `maxGroundOffsetStuds` to bound the absolute sampled sole distance from the estimated rest-ground plane; this requires a joint Studio identifies as a foot and is not collision physics. For a grip or other fixed target, supply both `targetPosition:[x,y,z]` and `maxTargetDistanceStuds`; coordinates are relative to the rig pivot and every contact sample must stay inside that radius. Missing pivot-local telemetry yields `unknown`. These are authored review constraints, not inferred targets.

To constrain a grip's facing as well as its position, supply `targetOrientation:[x,y,z,w]` as a unit quaternion in the rig-pivot-local frame and `maxAngularTargetErrorDegrees`. This checks each sampled orientation against the desired target; it differs from `maxAngularDriftDegrees`, which only checks change from the first contact pose. Missing orientation data yields `unknown`.

Each contact subcheck includes the Studio `sampleIds` used to measure it, so an agent can inspect the exact supporting poses. Persisted plan history retains these evidence IDs.

`jointMap` source-name lookup is case-insensitive, consistent with required-track and contact validation. If multiple map keys differ only by case and match one source joint, that assertion fails as ambiguous instead of guessing a target.

Persisted test-plan runs also enforce their pinned source fingerprint: a result with changed recipe content is accepted only as a failed run with an explicit `asset_fingerprint` check that records the observed and expected hashes. This prevents malformed run records from appearing as passing regression evidence.

Use `motion_animation_test_suite` to state explicit requirements for 1–8 unique clips and evaluate them on the same connected Studio rig. Clips are sampled sequentially because Studio has one stateful viewport; Motion Tools verifies the active rig ID and topology signature throughout and after the run. If the rig changes, affected samples become incomplete. Each test case can optionally include `expectedFingerprint` to pin the exact reviewed recipe; the returned fingerprint can be stored with the test contract and supplied on later runs to detect same-ID content drift. Cumulative travel is the sum of adjacent sampled distances and can miss movement between samples. The step-speed check identifies its worst adjacent sample pair and time range. All contact measurements depend on the interval's sample density. Supply the optional suite-level `jointMap` for recipe names that differ from target-rig names. A required track passes only when it exists in the recipe and Studio telemetry confirms it maps to a driven joint on the sampled rig; missing live evidence is `unknown`, and an unmapped target is `failed`. Disabled or zero-weight layers do not count toward the active angular-speed limit. Contact effectors must also resolve to driven target joints. Every check is `passed`, `failed`, or `unknown`; missing Studio evidence makes a case `incomplete`, not passed. The suite reports `passed` only when all requested criteria are measured and satisfied. This is a reproducible contract for project requirements—not an artistic score or release certification. It does not prove rendered deformation, collision physics, or behavior between samples. Use the measured contract alongside human visual review.

### Assemble animation from saved poses

When either pose preview inserts an interior key, it inherits the source segment's outgoing easing style, direction, and Bezier handles. This preserves the interpolation settings on the new outgoing segment; it does not claim the original curve shape remains mathematically identical after the pose changes the segment endpoints.

Pose previews target the base animation tracks by default. To author into an animation layer instead, pass that layer's exact `layerId` to `motion_pose_preview` or on the specific `motion_pose_sequence_preview` placement. Layer-targeted previews leave base tracks unchanged, return the full composed recipe, and bind the destination layer ID into the reviewed candidate fingerprint; same-time conflict traces are scoped to their destination layer. A sequence can direct different poses to different layers. `diagnostics.destinationLayerEffects` flags disabled and zero-weight targets and identifies overlapping later active layers that may change the composed result. Bounded `placementCompositionEffects` compare the composed local pose at each authored beat against a counterfactual with only that destination key restored to its original sampled pose; this measures recipe-composition impact at that time, not rendered deformation or overall visual quality. Layer-local endpoint deltas are reported only when both adjacent beats target that same layer; use `transitionMotion` for sampled composed motion across the full layered recipe.

Pose-sequence previews also return `diagnostics.markerBeatAssociations`: an unchanged advisory mapping each authored marker within 0.25 seconds of a placed pose beat to the exact or nearest beat(s), with signed offsets and explicit tie groups. It never moves/removes markers or asserts causality. `transitionMotion` provides easing-aware, composed local-channel samples between distinct-time pose beats. It lists the top eight per-joint position/angular speed and acceleration peaks with timestamps and bounded `eventContext`: up to four markers within 0.25 seconds of a peak (exact peak-window matches first), plus up to four declared contact windows intersecting its refinement window, labeled active at the refined peak or overlapping only the window. Signed marker offsets and omission counts retain timing and disclose truncation. This is authored temporal context—not causal attribution, physical contact, or proof of a visible event. The target coarse rate is 60 Hz, but a global evaluation budget can reduce it; check `effectiveSampleRateHz`. The strongest 16 coarse peaks per signal receive local neighborhood refinement up to 240 Hz when budget allows. Each result includes its coarse and refined value, refinement window/rate, and `resolvedWithinFivePercent`. This compares those samples only—it is not an error bound and cannot reveal an event missed entirely by the coarse pass. These are diagnostic measurements, not quality thresholds, and do not establish rendered body motion or contact.

Budgeting accounts for per-interval sample rounding and authored key times. All coarse intervals are sampled before local refinement is allocated, and `coarseEvaluationCount` / `evaluationCount` are bounded by the returned coarse/total budgets. The analyzer accepts only up to 31 valid chronological, non-overlapping intervals within the clip.

### Build a trigger-driven animation graph

#### Runtime controller example

When the timeline simulator returns composed poses, each joint also reports `rotationBlendConfidence`, a normalized principal-eigenvalue gap: 1 indicates a dominant mean orientation; values near 0 indicate an ambiguous rotation blend, not a precise target. `rotationInfluence` reports total effective animation weight; the remainder is `residualWeight`. After `motion_animation_graph_runtime_export` returns reviewed module source, place it in a `ModuleScript` and integrate it from the intended authority context. For a server-owned player controller:

```lua
local Controller = require(path.To.GeneratedController)

local binding = Controller.BindToPlayer(player, function(controller, character)
    controller:ConnectMarker("Impact", function(markerName, markerValue, stateId)
        -- Validate gameplay state before applying damage or spawning effects.
        print("Animation marker", markerName, markerValue, stateId)
    end)
end, { preloadAll = true })

-- Call only after the game has authorized this action (for example, in a validated server handler).
local ok, result = binding:TriggerWithParameters("Attack", {
    stamina = 0.8,
    grounded = true,
}, "heavyAttack")

if not ok then
    warn("Animation transition rejected", result.reason or result.noTransitionReason)
end

-- On teardown:
binding:Destroy()
```

The generated controller also exposes `GetBlendState()` for live diagnosis. In an active BlendSpace state it reports the driving parameter and clamped sample value plus each source clip's authored expected weight, Roblox `WeightCurrent` and `WeightTarget`, authored source-state speed, effective phase-aligned speed, observed `AnimationTrack.Speed`, loaded/playing state, and summed observed weights. The controller speed and authored clip durations determine effective sample speed; the sample state's own graph `speed` does not apply independently while it is a BlendSpace source. It returns `current_state_not_blended` when the active state is discrete. Player bindings forward the same query to the current spawn, or return `controller_not_ready` before a character controller exists. `WeightCurrent` can differ from `WeightTarget` during fades; an agent should compare them as separate measurements rather than treat target weights as proof of the current visible pose.

`GetBlendState()` also returns observed `AnimationTrack.Length`, `Speed`, `TimePosition`, and normalized phase when available, plus `phaseSync` with measurement completeness, unavailable source IDs, and the maximum wrap-safe phase difference among currently playing samples. Its `simulationTimingCalibration` object is ready only when every source length and playback speed is available; when ready, `observedBlendAnimationLengths` and `observedBlendAnimationPlaybackSpeeds` are nested controller/source maps directly consumable by `motion_animation_graph_timeline_simulate` or a timeline-test case. If every sample is currently playing and has a readable `TimePosition`, it also provides `observedBlendAnimationStartPhases`, allowing a simulation to begin at the observed phase instead of incorrectly resetting all clips to phase zero. It includes `animationIdsByStateId` and `assetSetFingerprint`. To run a measured simulation, pass that fingerprint as `observedBlendAnimationAssetSetFingerprint` and the `assetSetFingerprint` returned by the matching `motion_animation_graph_runtime_export` as `expectedBlendAnimationAssetSetFingerprint`; the simulator rejects missing pairs and mismatches. This detects accidental stale snapshots or mixing measurements from another export. While any source measurement is unavailable, it reports unavailable source IDs and withholds partial simulator maps. Call it again after Roblox has loaded all clips. This is a live snapshot rather than a durable signature; use it immediately with those same published assets. `Length` can remain zero until Roblox finishes loading an animation, so observed calibration is omitted until lengths are valid. The actual `Speed` map is important because playback may not yet have called `SynchronizeBlendPlayback()`; the simulator uses measured speeds directly rather than assuming the synchronized ratio. The simulator and runtime measurements can expose a published asset whose timing differs from its authored recipe. Timeline simulation can also take measured per-source Play-retrigger profiles: a measured `preserved` behavior keeps that source clock running while it fades, while `reset_to_zero` (or missing/ambiguous evidence) resets its modeled clock and updates preservation/reset evidence counters. This is especially relevant when the same BlendSpace source channel is reused across a self-transition or re-entry.

`motion_animation_graph_timeline_simulate` and each `motion_animation_graph_timeline_test` case can accept `observedBlendAnimationLengths` and `observedBlendAnimationPlaybackSpeeds`, each keyed first by BlendSpace controller state ID and then by sample state ID. Supplying measured calibration requires complete, key-matched maps and both the runtime snapshot and expected export `assetSetFingerprint`; missing pairs or mismatches are rejected. Optionally supply a complete `observedBlendAnimationStartPhases` map from that same snapshot to seed each source clock at its captured normalized phase; this map requires matching complete lengths and speeds. Actual measured speeds drive each sample clock, accurately reflecting whether runtime synchronization has occurred; without live maps, authored recipe duration ratios remain the estimate. During parameter changes, a channel faded to zero with `AdjustWeight(0)` remains clock-active; if a targeted channel has naturally ended, it restarts at the first still-playing source’s normalized phase. The modeled parameter update fails closed without any usable source clock. Timeline events report restarted state IDs, phase source, or failure reason. Authored poses and marker phases are mapped through normalized progress. `blendModel.phaseSynchronization` and timeline-test `blendSpace.phaseSyncThroughout` share the same maximum pairwise circular normalized-phase analysis at sampled points and across constant-speed intervals between them, detecting a half-cycle peak that falls between output frames. Both report the worst time/interval/source pair and explicit coverage counts; timeline tests additionally gate against the requested drift tolerance. Interval evaluation assumes constant per-source playback speeds between simulated samples. Results distinguish observed, incomplete, unevaluable and successfully evaluated points/intervals; `not_observed` or `incomplete` coverage is not a pass, and the timeline gate fails closed if any active source clock is stopped or active interval cannot be measured. `blendModel.playbackTiming` reports timing provenance, observed lengths, start phases, effective speeds, each clip’s modeled cycle duration, and its ratio to the controller clip. Individual timeline blend assertions can also gate `playback.playbackCycleDurationRatioToController` for a specific clip and timestamp. Ratios other than 1 expose a modeled timing offset but do not predict the engine’s natural-end fade or claim rendered-quality evidence. Immutable timeline plans preserve the exact maps and fingerprints in their suite fingerprint; run reports retain per-case details and a top-level `playbackTimingFingerprint`, and comparisons mark changed maps as different blend models. Fingerprints and measurements remain caller-supplied (not cryptographically authenticated); use fresh values from the same published assets. The simulator remains an estimate, not a live Roblox engine execution.

When live phase drift is confirmed, generated controllers expose `SynchronizeBlendPlayback()`. It requires every active source track to be playing with a positive loaded `Length`; it then sets the first sample to the controller's configured speed, derives other speeds from actual Roblox track-length ratios, and seeks every sample to the first sample's current normalized phase. The measured speed ratios are retained for that controller state, so later parameter-driven channel restarts and state re-entry keep the measured timing. This is an explicit operation because aligning an already-drifting clip can visibly seek its pose. It reports per-source old/new speed and time, and rolls back attempted changes if Roblox rejects an update. If source lengths are still unavailable, wait until Roblox loads them and retry; the operation does not guess from authored duration.

When a parameter changes during the transition into a blend controller, the runtime retargets the clip weights using the remaining crossfade time instead of snapping to full blend weight. Once that entry fade completes, parameter-driven adjustments are immediate. The simulator independently estimates each source track through entry, retarget, and exit fades; its explicit `targetPoseContributionWeight` assertion can gate intended values separately from current estimated values. Roblox's live `WeightCurrent` remains the authority for what the Animator is currently blending.

`motion_animation_graph_fade_calibrate` also captures native `AnimationTrack:AdjustWeight` fade-in and fade-out curves on the detached rig. Version 4 profiles persist these curves alongside the existing Play/Stop, repeated-Play and natural-completion measurements. When a BlendSpace source channel is retargeted during a matching fade duration, `motion_animation_graph_timeline_simulate` and `motion_animation_graph_timeline_test` rebase the measured AdjustWeight curve from the channel's actual simulated current weight to its new target; upward and downward retargets use separate curves. Older profiles, missing curves and unmatched durations keep the documented linear estimate. The report includes applied profile fingerprints. This calibrates fixed fade durations on the captured Studio build; it does not certify engine scheduling or the whole game.

Fade calibration waits up to five seconds for the detached `AnimationTrack.Length` to become positive before measuring natural completion. Roblox documents zero as “not yet loaded”; if the length remains zero or exceeds the supported 30-second limit, calibration fails without persisting a profile. Stored and directly supplied natural-completion profiles must have a positive measured length, preventing an unloaded track from being treated as an instantaneous clip.

## Studio commands

Choose a rig in the Motion Tools **Rig Library** before calling `motion_studio_sessions`. The result includes the connected session and active rig ID. `snapshot.motionEditor` reports the latest plugin heartbeat's open viewport/rig/clip, saved-vs-candidate and dirty state, playhead/play status, selected joint/key, timeline window, and orbit camera parameters; its `fieldAvailability` distinguishes no clip, no selected joint, closed/unavailable camera, and fields requiring a fresh draft read. `motionEditorContextAssessment.freshness` is `fresh` only while online with `heartbeatAgeMs` under 10,000; otherwise it is `stale` (or `unknown` when age is missing). `motion_agent_resume` returns the same assessment so reconnecting agents can make this decision immediately. Existing Workspace humanoid rigs can also be chosen from the same list without changing or moving the original. When multiple Studio sessions are connected, specify the session explicitly.

`motion_studio_inspect` returns the driven hierarchy, retarget profile and, for each part-backed animated node, a `visualGeometry` cue with `BasePart.Size` dimensions in studs, part class, transparency and `Part.Shape` when available. Each animated hierarchy entry also carries its Roblox `targetKind` (`Motor6D`, `AnimationConstraint`, or `Bone`); the server checks that this matches the corresponding retarget-profile node before exposing it. This identifies the driver class, not mesh skinning, local axes, or joint limits. Older saved profiles may omit the optional field. On successful `motion_studio_job` polling, the server validates requested rig identity and profile topology, then returns `aiRigSummary` with the exact `directlyAnimatableJointNames` allow-list, non-driven names, parent/segment hierarchy, compact semantic-role statuses, and `jointCapabilities`. The latter joins exact parent, `animationChannelAllowed`, and `visualCloseUpStatus` for each profile joint, avoiding name-based cross-referencing. Only `visualCloseUpStatus: eligible` may be used as a capture `focusJoint`; other statuses explain whether the joint is non-driven, a Bone without an independently focusable part, missing a validated inspection node or part geometry, not Studio-approved for capture, or fully transparent. Use only the exact driven names as animation channels. `exact` means a standard R6/R15 name convention; `inferred` means unique joint-name tokens only; neither proves anatomy. Ambiguous/unavailable roles have no safe automatic target, and R6 hand/foot cues can alias the whole arm/leg segment rather than a separate wrist/ankle. This gives an AI a fast capability map without asking it to infer from names alone. Part geometry remains a coarse measure of the segment represented by a channel; it is not a mesh's tight bounds, per-bone skinning influence, silhouette, color/material, or anatomy. Bone nodes intentionally have no fabricated per-bone geometry. Use the dedicated viewport and approved image capture for rendered visual review. For details that are too small in a whole-rig image, add `focusJoint` (an exact part-backed animated-node name with `visualCloseUpStatus: eligible`) to a requested capture frame. Studio centers and zooms the disposable capture clone on that part and its immediate parent/child segments; the original rig and camera are restored afterward. The focus name is carried through the PNG metadata, capture-coverage checks, and review attachment so another joint's screenshot cannot accidentally satisfy the focused request. Bone-only nodes and unknown names fail closed; the focused still still cannot establish mesh deformation or skinning quality.

After `motion_studio_inspect`, `motion_studio_probe_joint_axes` can empirically measure small positive/negative local X/Y/Z Euler pulses on one exact driven joint of the active, freshly inspected rig. Studio samples the bounded disposable recipe on its detached evaluator clone. The result includes a `jointContext` bound to the inspected parent, driver class (or `null` for an older profile), and segment length; this identifies the measured hierarchy channel but does not establish its axes or anatomy. The result also includes a central-difference local rotation response Jacobian, positive/negative asymmetry, directional descendant joint-pivot displacement responses, and explicit diagnostics for near-zero or asymmetric response; it does not save or apply a pose to the editor. The Jacobian maps input recipe XYZ degrees to measured angular-vector degrees relative to the clone's zero-input recipe sample—not the original rig's rest orientation. It is only a small local approximation around that baseline for the current topology, not a global inverse solver, anatomy, joint limits, contact, mesh deformation, or artistic quality. Treat `unresponsive` and `asymmetric_or_coupled` results as requiring review, not as calibration. Visually review authored motion. The subsequent `motion_studio_suggest_local_rotation` response retains the same `jointContext` so the preview request can be interpreted against the same measured hierarchy node.

Use the `probeId` returned by `motion_studio_probe_joint_axes` with `motion_studio_suggest_local_rotation`, along with the exact source animation recipe, its SHA-256 `expectedSourceFingerprint`, a target time, and a small desired angular correction relative to the measured zero-input recipe pose. The full probe stays in server memory for five minutes (an MCP process restart clears it), avoiding a bulky copy/paste and preventing fabricated or cross-rig calibration input. Suggestion lookup is bound to the same connected session and freshly inspected active rig topology. It refuses unresponsive/asymmetric probe evidence, singular or ill-conditioned Jacobians, solutions beyond the 15-degree local envelope, non-neutral or missing keys, enabled layers or root motion affecting the joint, and declared contact at the matched key time. This is intentionally conservative: `set_pose` replaces an absolute key rotation, so only a neutral exact key can safely receive this small correction. The result returns `patchPreviewRequest`; pass it with the same source recipe to `motion_animation_candidate_patch_preview`, inspect the fingerprinted candidate and channel impact, then use the existing viewport preview/apply flow. The tools do not directly edit or save the animation.

Scene operations return a job ID. Call `motion_studio_job` to check its status:

- `queued`: waiting for the plugin
- `running`: delivered to Studio
- `succeeded` or `failed`: confirmed by the plugin
- `expired`: never delivered within the allowed time
- `unknown`: delivered, but no result arrived in time

If an agent loses track of a command ID, call `motion_studio_jobs` with the session ID from `motion_studio_sessions`; when exactly one Studio session is online, the session ID may be omitted. By default, it lists queued, running, and unknown jobs. Set `includeTerminal=true` to include recent completed, failed, expired, and cancelled jobs. The listing intentionally omits command payloads and result bodies; use `motion_studio_job` with a returned ID to fetch a confirmed result. For `unknown`, inspect the plugin/scene and check that job before retrying to avoid duplicating an operation that may have completed.

The production server keeps a local, bounded `artifacts/studio-job-journal.json` with up to 256 job IDs, session IDs, operation names, timestamps and statuses—never command payloads or results. `motion_agent_resume` exposes these recovered entries across plugin session changes. After a server restart, an undelivered queued job becomes `expired`; a delivered job becomes `unknown` because Studio may have applied it; a terminal status is retained but its result is unavailable. No command is automatically replayed. Inspect Studio and re-run inspection when result data is needed. When the in-memory queue reaches capacity, it reclaims only the oldest known-terminal entries; queued, running and unknown jobs are protected. If capacity is entirely unresolved work, new commands are rejected with an instruction to inspect and resolve jobs. A malformed journal fails closed at startup rather than silently discarding recovery state.

`motion_review_list` provides a paginated, validated inbox of recent review revisions, including reviews waiting for user feedback, interrupted operations, and records rejected for malformed data or mismatched asset ancestry. `offset` pages valid review summaries; `invalidOffset` separately pages record-level diagnostics, with `invalidRecordCount` and `nextInvalidOffset` indicating remaining failures. Reading a review or listing the inbox never changes saved history. After a server restart, use `motion_review_recover` on a record with `recoveryRequired: true`; it records one new immutable revision returning the review to its last safe feedback state, without retrying Studio or provider work. `motion_agent_resume` includes a compact recent inbox and recommends recovery or user-feedback actions without performing either one.

Call `motion_agent_readiness` before an animation authoring or review task when the agent needs a single explicit preflight. Optionally provide `sessionId`, `rigId`, `assetId`, `workflowId`, up to five unique `requiredStudioFeatures` from `poseSampling`, `animationLibrary`, `fullBodySnapshots`, `inverseKinematics`, and `editorDraft`, exact unique `requiredStudioOperations`, and unique `requiredSemanticRoles` needed by the action. Prefer exact operation requirements when known: `readEditorDraft` and `applyEditorCandidate` are checked independently, as are rig inspection, pose sampling, local animation browsing/open/save, export validation, candidate/editor-draft capture, and IK. It checks recent Studio connectivity, unambiguous session selection, active rig identity, a fresh successful inspection from that same live session, unresolved Studio jobs, requested features and operations reported by the plugin heartbeat, required role resolution, and (when requested) saved animation provenance against the active topology. Exact R6/R15 convention roles are ready; unique custom name-token matches are unknown; ambiguous/unavailable roles block. Capability/operation metadata missing from an older plugin is `unknown`; an explicitly false requirement is `blocked`. The result returns the reported plugin version and both manifests when available. It does not probe screenshot/rendering permission/support or infer capabilities from a version number. `ready` means only that requested technical prerequisites were observed; `blocked` means an explicit prerequisite failed; `unknown` means the available evidence cannot establish readiness. It does not certify artistic quality, visual review, gameplay correctness, export, or publishing. The tool is read-only and never retries commands.

`motion_animation_blueprint_preview` accepts either an exact `joint` name or one standard `semanticRole` per pose (never both). Semantic-role poses require a fresh active-rig binding with `sessionId` and `rigId`; only exact recognized R6/R15 mappings compile. The result includes `rigValidation.semanticRoleMappings`, preserving the resolver evidence (including the R6 hand/foot endpoint-alias caveat), and is fingerprint-bound to the resolved blueprint and inspected rig profile. Custom-rig name guesses are deliberately rejected by this shortcut: resolve candidates with `motion_animation_resolve_rig_semantics`, inspect the rig, and then supply the reviewed exact driven-joint name. The compiler still requires explicit poses and never generates animation intent by itself.
- `cancelled`: an inspection was cancelled before its command was delivered

Inspect the scene before retrying an unknown result. Commands are delivered only once and target the model ID captured during inspection. Changing the selection does not redirect them.

Before a solve, use `motion_ik_target_path_analyze` with either a saved `assetId` or inline `samples` (exactly one), an interpolation mode, and a sample rate. It reports sampled curve length, mean/peak speed, peak finite-difference acceleration, per-waypoint chord speeds, and maximum curve deviation with the worst segment and time. It also returns `targetPathFingerprint`, a canonical SHA-256 over validated timed samples. Pass this as `expectedTargetPathFingerprint` to `motion_studio_ik_contact`, or on the matching constraint in `motion_studio_ik_constraints_preview` / apply, so a changed waypoint list is rejected before the solve is queued. This guards path identity, not interpolation settings or world-frame suitability; preserve those choices and the same place coordinate frame yourself. Optionally supply project-specific maxima for peak speed, peak acceleration, and deviation; only caller-supplied criteria produce `passed`/`exceeded` checks and warnings, avoiding a universal artistic threshold. Use these observations to revise paths that appear too fast or bend too far. These metrics do not estimate limb reachability or certify smoothness between samples; always inspect the actual Studio solve and residuals.

For a single end-effector pose, use `motion_studio_ik_pose`. For a reviewed, fingerprint-guarded IK edit, `motion_studio_ik_constraints_preview` accepts one to four effectors. It accepts exactly one source: either a saved `assetId`, or a complete unsaved animation `recipe` (such as a blueprint preview); recipe mode derives a deterministic ephemeral Studio identity and does not save a library asset. For a planted/support or grip interval, use `motion_studio_ik_contact` with `limb`, `startTime`, `endTime`, optional world-space `offset`, and `sampleRateHz` (15, 30, or 60; default 15). Set `toleranceStuds` (0.001–0.5, default 0.05) to control the CCD early-stop threshold and classify each sample. The result's `solve.status` is `converged` when every sample meets tolerance, `partial` when at least half do, or `unmet` otherwise; inspect `unmetSampleTimes` and the residuals. `unmet` means this bounded solve missed the requested precision—not proof that a target is anatomically unreachable. Without a target path, the start pose determines one fixed world-space endpoint target. To track a moving prop or support, pass either inline `targetPath` points or `targetPathAssetId` from the reusable library (never both). Create a reusable asset with `motion_ik_target_path_save`, search it with `motion_ik_target_path_list`, and inspect its fingerprint and points with `motion_ik_target_path_read`. A path contains 2–32 strictly ordered `{time, position:[x,y,z]}` world-space samples and must cover the complete solve interval. It is immutable and fingerprint-checked, but coordinates are only meaningful in the same Studio place/world frame; it is not attached to a moving part or normalized to a rig. Set `targetPathInterpolation:'centripetal_catmull_rom'` to smooth sparse waypoint motion; the default `linear` mode preserves exact waypoint-to-waypoint travel, while the cubic curve may overshoot between authored positions. The selected mode is included in coordinated-IK fingerprints and returned solve evidence. The plugin adds optional offset to every evaluated target. Optional `poleTarget:[x,y,z]` is a fixed world-space point that steers the elbow/knee bend plane for limbs with at least two segments; it is not the endpoint target and is held fixed through the interval. The returned `bendPlane` report measures projected bend-direction deviation over time; see the next paragraph for degenerate cases and limitations. The plugin samples the interval plus authored key times, solves the selected limb chain at each sample, and returns per-time endpoint residuals and a complete unsaved recipe. The solve is bounded to 128 sample keys and rejects track/key-cap overflow. It currently supports the base track and Override layers, not Additive layers. Use `motion_studio_job` to confirm completion, inspect residuals, open and play the returned recipe, then save it with `motion_library_save` using the original asset as `parentId`. This is sampled CCD editing—not collision-aware IK, a ground detector, or proof of physical contact. Targets are world-space in the Studio viewport; actual in-game root movement or moving-platform transforms need separate validation.
When `poleTarget` is set, the result also includes `bendPlane`: per-sample unsigned angle between the limb's projected bend direction and the projected pole direction, plus maximum error/time, RMS error, and explicit unmeasured times. `measured`, `partial`, and `unavailable` indicate measurement coverage, not quality. Straight limbs, missing chain pivots, and pole points on the limb axis can make a sample unmeasurable. This metric is separate from endpoint residual and does not replace visual review.

For a full clip with alternating or overlapping support windows, use `motion_studio_ik_contact_bake_preview` with the exact hand/foot effectors to process all their declared support/grip intervals. Provide exactly one `assetId` or inline animation `recipe`; a rig-bound unsaved blueprint recipe can be baked directly without a throwaway library save. Inline recipes are checked against a fresh inspection of the currently selected rig, including driven tracks and the requested contact effectors. Each contact is anchored to its own world endpoint at its start; overlapping limbs solve together, every distinct authored key time and declared contact boundary inside the contacts is sampled exactly, and the combined time/key budget is checked before Studio edits anything. Only redundant generated grid samples within 0.1 ms of a required time are coalesced; required authored/boundary times are never merged, and a near-boundary gap does not activate contact early. The plugin and MCP server independently build the schedule and require the returned Studio timestamps to match preflight within 1 ns; mismatches are rejected. The preview returns residuals per source contact index, so an AI can identify exactly which plant needs help. Abutting contacts for the same effector transfer the shared boundary to the newer contact, anchoring it from the pose already solved at that boundary. Contacts remain author-declared intent: the tool does not discover missing plants, infer moving-platform transforms, or prove ground truth. It does not save the animation. Visualize the returned fingerprint with `motion_studio_ik_constraints_visualize`, inspect the ghost across the entire clip and every per-window residual, then apply through `motion_studio_ik_contact_bake_apply` with the identical inputs and candidate fingerprint. Apply recomputes the complete candidate and evidence; it edits only the unsaved viewport draft. Candidates expire after five minutes and on server restart. Save a child library revision separately after visual review.

For actions that require multiple planted/gripping limbs at once over one shared interval (for example, both feet plus a weapon hand), use `motion_studio_ik_declared_contacts_preview` when the saved animation declares exactly one matching interval per selected limb. For custom targets or different intervals, use `motion_studio_ik_constraints_preview` with one common interval and 2–4 unique limbs; each constraint may have its own fixed start target or inline/saved moving position path. You may also provide exactly one orientation mode per constraint: `targetOrientationDegrees:[x,y,z]` for one fixed world-space orientation, or `targetOrientationPath:[{time,orientationDegrees:[x,y,z]}, ...]` for 2–32 ordered world-space XYZ Euler waypoints. The orientation path must cover the full solve interval; Studio interpolates between explicit waypoints with `CFrame:Lerp` (shortest-arc rotational slerp), preserving the endpoint's world position while returning angular residuals per sampled time. Set `orientationToleranceDegrees` (0–180 degrees, default 5) to classify these measurements: every sample reports its measured error and within-tolerance flag, while `orientationEvidence` reports converged/partial/unmet coverage separately from positional residual status. This is a mechanical tolerance, not an artistic-quality threshold. Orientation targets are in the Studio world frame—not attachments to moving props, inferred grips, or proof that the hand visually aligns. Both position and orientation targets and tolerances are included in the preview/apply identity and returned solve evidence. The plugin computes a full candidate recipe and per-limb residual series, then restores the viewport recipe and undo history. Shared ancestors—such as the hips/root in a two-foot stance—are handled with deterministic alternating CCD sweeps: each effector is solved in stable limb order, then all endpoint residuals are remeasured together. This is a bounded compromise solver, not a global least-squares optimum; inspect the final residuals and expect `partial` or `unmet` when the goals conflict or the rig cannot satisfy them. To see the actual candidate motion on the rig before applying it, call `motion_studio_ik_constraints_visualize` with the returned `candidateFingerprint`; it displays a translucent cyan ghost separate from the editable rig and can play, loop, and change playback speed. For coordinated-IK previews it also places amber labeled requested targets in the viewport; moving targets follow the exact solve path and are hidden outside the solve interval. The visual overlay is temporary, cannot be saved, and does not dirty the editor recipe. Use `motion_studio_ik_constraints_clear_preview` or the banner's × button to remove it. To apply the exact reviewed result, call `motion_studio_ik_constraints_apply` with the same normalized inputs and the `candidateFingerprint` returned inside the successful preview job result. The server binds that fingerprint to the source recipe, resolved target paths, orientations, tolerances, settings, selected rig and topology; the plugin recomputes the solve and compares both the complete recipe and residual evidence before changing the viewport draft. The apply operation edits only the unsaved viewport draft; save a child library revision separately after review. The legacy `motion_studio_ik_constraints` remains as an immediate mutating path, but should be avoided. All modes still use bounded sampled CCD and do not account for collisions, moving-part attachment transforms, or global body-balance optimization.

For AI-visible target-versus-pose review, pass the exact coordinated-IK `candidateFingerprint` as `ikCandidateFingerprint` to `motion_studio_capture_candidate_views`, together with the full candidate `recipe` returned by the preview and its session/rig. The server rejects stale, applied, or mismatched candidates and annotates each screenshot with colored 3D endpoint targets evaluated at that frame's time; the stable legend is LeftHand=amber, RightHand=coral, LeftFoot=violet, RightFoot=mint. The completed job returns this legend plus `ikTargetGuideCoverage`; each entry includes `captureId`, `time`, `view`, active `limbs`, and each active limb's exact `targetWorldPosition` in the Studio world frame after the solver offset. Path coordinates use the shared IK path evaluator and selected interpolation. When the AI retrieves the PNGs, each image's `visualReviewTemplate.ikTargetGuideEvidence` repeats the exact candidate fingerprint, legend and target coordinates beside its matching image. These coordinates describe requested intent, not measured limb endpoints; the model must inspect the actual PNG and report occlusion or ambiguity honestly. Captures use an isolated posed clone, include the rig and target points in camera framing, and omit targets outside their solve interval. Three-dimensional markers are used because Studio screenshots exclude UI layers. Screenshot permission still applies. The PNGs are visual evidence for the connected AI to inspect, not an automatic quality verdict; captures do not modify the live viewport or editor draft. This annotation is available for coordinated IK candidates, not arbitrary recipes or contact-bake summaries.

Each coordinated constraint may also specify `poleTarget:[x,y,z]` in Studio world space. This steers the limb's projected bend plane toward that point, helping stabilize elbows and knees while endpoint targets are solved. The pole target is held fixed during the interval and is bound into the preview/apply fingerprint. It is ignored on chains shorter than two segments and cannot force a valid bend when the limb is straight or the pole lies on the root-to-endpoint axis. Endpoint residuals do not measure pole alignment; inspect the candidate silhouette and confirm the limb does not flip.

Rigid-part connections preserve rest positions and anchoring. Check anchors before using the rig in gameplay. Duplicate animated names and joint cycles are rejected. Rigs that combine Bone and Motor6D animation need a separately selected sub-rig in this version.

Use `motion_studio_preview` to review an animation with up to 12 VFX cues. A cue can use `{time}` for an exact second or `{marker, occurrence?, offset?}` to follow a named marker in the animation recipe. Occurrence is 1-based and defaults to 1; offset is signed seconds. Missing markers, offsets before zero, and cues outside either the animation or preview duration are rejected before a Studio job is queued. On Motion Tools-managed rigs, effects are attached to the viewport clone and never inserted into `Workspace`; `motion_studio_stop_preview` removes active effects and stops playback. The legacy Workspace clone remains for ordinary Workspace rigs. ViewportFrame rendering differs from the game camera (including lighting and post-processing), so treat it as an authoring preview and verify the result in-game.

For reusable effect passes, first call `motion_vfx_timeline_preview` with the animation asset ID and 1–12 VFX cues. Inspect each resolved part, cue time, marker occurrence and exact source fingerprint. Commit only the returned `candidateFingerprint` through `motion_vfx_timeline_create`; use `motion_vfx_timeline_update` to make a child when changing the arrangement or adopting different source revisions. Saved entries fingerprint both their cue-sheet contents and pinned animation/effect sources. Read/list report `verified`, `stale`, or `corrupt`; corrupt entries remain visible in listings but cannot be read or played. Before Studio playback, call `motion_studio_vfx_timeline_preflight` on the selected rig and check its job result. It evaluates the exact animation at every cue and constructs each effect on a disposable clone. Only a successful result issues a five-minute capability; pass its `preflightFingerprint` to `motion_studio_preview_vfx_timeline`. The capability binds the session, rig topology, cue-sheet fingerprint and joint mapping. Cue sheets store asset references and fingerprints, not duplicate animation/effect recipes.

## Animation recipes

Plan motion in readable poses, then timing, then purposeful breakdowns and secondary motion. Inspect the selected rig first; its report gives driven names and parent links but does not determine custom axes or artistic quality. Run `motion_animation_audit` for heuristic flags and always preview the full result in the plugin viewport before saving. For exact rig coverage, pass both `sessionId` and `rigId` from a fresh inspection. The optional `rigCoverage` binds the result to the inspected topology, reports active authored channels for each driven joint, unresolved exact-name tracks, and inactive/zero-weight layer channels. Untracked joints are cues to inspect, not errors; intentional stillness is valid. Offline audits omit this section rather than guessing.

### Rig provenance and retargeting

Animation assets may carry a `sourceRigProfile` containing the inspected rig's stable ID, topology signature, driven hierarchy, rest-space bases, and segment lengths. New AI-generated animations attach the profile when a rig was inspected. For `motion_library_save`, pass `sourceRigProfile` directly or pass `sessionId` and `rigId` to attach a recent successful inspection of the selected rig. Ordinary child revisions inherit the parent's profile; `motion_animation_retarget` records the target profile on its child. Legacy assets without provenance remain valid and can still be retargeted by supplying `sourceProfile` explicitly. Library listings expose only the source rig ID/name/type, while full profiles are returned when reading an asset. Imported animations additionally retain integrity-checked `importProvenance`: Roblox source identity, recipe fingerprint, rig-geometry fingerprint and provenance fingerprint. For local AnimSaves clips, identity uses the sequence name plus stable source geometry and recipe, not Studio's transient in-memory rig ID, so reconnects do not break retry identity. Asset reads reject mismatched import IDs or altered provenance/content.

For an animation with saved provenance, `motion_animation_suggest_joint_map` can use that source profile and a recently inspected selected target by passing `sessionId` and `targetRigId`. The target signature must still match and cached inspections expire after five minutes. The retarget tool accepts the same source/target IDs and uses stored source provenance automatically. Explicit profiles remain supported. Mapping suggestions never apply themselves; review the candidates and explicitly confirm mappings before retargeting.

### Targeted animation patches

For incremental AI edits to a pose, `offset_pose` adds joint-local XYZ translation in studs and/or composes a Roblox XYZ Euler rotation offset in degrees after the current rotation in quaternion space. Its change summary includes the pose before and after the edit so an AI can inspect the exact result without inferring it from the requested delta. By default it requires an existing key; set `insertIfMissing: true` to explicitly create a breakdown by interpolating the track before applying the offset. This insertion is interior-only and obeys the track key limit. Zero-effect offsets are rejected. Use `set_pose` for absolute transform values. Both are previewable and fingerprint-guarded through the normal patch workflow.

Use `offset_pose_group` when one pose beat needs coordinated changes across multiple joints. It applies two or more unique, exact-case joint targets at one shared time and layer, preflighting every track/key before changing any target. Each joint gets its own before/after pose and requested offset in the change report. `insertIfMissing: true` interpolates interior breakdown keys for all missing target keys, subject to the same key limit; if any target fails validation, the group operation changes none. Preview the complete patch and use `preserve` guards for unaffected joints or phases before committing the candidate fingerprint.

Evidence-linked AI review proposals may use one `offset_pose_group` as a single coordinated correction. The review system derives the affected interpolation window and composed-pose preservation regions independently for every target joint, verifies all other recipe data is structurally unchanged, and rejects rebasing if any target track differs from the reviewed source. Same-rig proposal evaluation reports per-target change status and proposes whole-rig capture frames for grouped edits rather than focusing on only one joint. These remain unsaved suggestions; inspect the exact preview and get user approval before applying or saving.

When a preview binds a contradicted visual finding, its `refinement.reviewPlan` places the exact cited frames and recipe-derived marker/contact context beside the proposed patch changes and caller-selected preservation guards. It requires the agent to confirm the edits address visible evidence, protect accepted surrounding motion, and re-capture the revised candidate. This is a review aid, not automatic proof that an edit fixes the cited issue or preserves unguarded motion; unsupported and unclear findings remain ineligible for visual-finding patch binding.

When `includeAudit` returns a `refinementTargetOutcome`, `still_ranked_in_region` means only that a candidate extremum remains in the mapped channel/time region. Read `measurementComparability` separately: `same_stencil` means the source sample window, derivative order/rate, and crossed-boundary kinds/times match after timeline mapping; `changed_stencil` means the numerical values are not a like-for-like measurement. Both source and candidate targets retain `measurementProvenance`, including exact windows and crossed key/phase boundaries. Key-segment indices may shift after edits and are not used as a cross-revision identity. Neither result is an artistic quality verdict.

Use `motion_animation_patch` when revising a saved animation without replacing the entire recipe. It accepts 1–50 ordered operations. A dry-run applies the complete batch to an isolated copy and returns the candidate recipe, source/candidate fingerprints, operation counts, affected targets, and detailed changes without saving a revision. To commit, repeat the exact `assetId`, operations and preserve constraints with `dryRun: false` and pass the returned `candidateFingerprint` as `expectedCandidateFingerprint`. Commits without that fingerprint, stale fingerprints, or changed candidates are rejected. Layer IDs created during a patch are deterministic for the exact source and request, so dry-run and commit resolve to the same recipe. A failed operation or final validation saves nothing. The `compress_track` operation adaptively removes redundant keys from one base or layer track using caller-specified maximum local position and quaternion angular errors. Its validation schedule includes a bounded uniform grid, every authored key, and quarter-points of each source key segment; `sampleRateHz` supports 30, 60, 120, or 240. Existing keys inside declared contact windows and keys at marker times are retained by default. The report returns original/retained/removed/protected key counts, sample count, and maximum measured errors with times. Tolerances apply at those samples, not mathematically at every continuous time or to rendered/physical motion. This can reduce dense imported or generated tracks before Roblox export while making the quality/size tradeoff explicit. Optionally use a surrounding `preserve` guard for composed motion in an important region. The `close_loop` operation turns a non-looping clip into a structurally loopable in-place pose cycle by sampling its existing curves and blending every base/layer track back to its initial pose over a chosen tail window, using shortest-path quaternion interpolation. It reports the maximum endpoint position/angular gaps before and after; earlier motion and root motion, contacts, and markers remain unchanged. Because the tail is rewritten, protect important late phases with `preserve` guards and preview the full candidate. Endpoint pose continuity is not velocity continuity, contact quality, or artistic approval. Preview the resulting child with `motion_studio_open_animation`, confirm the Studio job, then ask the user to review it before saving a native Studio asset.

For an AI-guided refinement, set `includeAudit: true` on the dry-run. The response adds `auditImpact`: before/after sampled local-channel speed, acceleration and jerk for changed channels; `unintendedChannelChanges` flags measured channel changes outside operation targets; `authoredChannelChanges` fingerprints exact track content so a direction/pose change cannot be hidden merely because speed magnitudes stayed the same; and `authoredChannelChangesOutsidePatchTargets` highlights recipe edits outside the operation targets. `refinementTargetOutcomes` tracks whether a prior ranked target remains in the same time region, remapping that region across clip/phase retimes. A target dropping out of the bounded list is not proof it is resolved. `unmeasuredCompositionChanges` flags edits to weighted/enabled/reordered animation layers and additive root motion because independent local-channel metrics do not compose them into final joint motion. `auditSampleRateHz` controls the comparison rate (30, 60, 120 or 240 Hz; default 60). This is a measured change report, not an automatic quality score: the AI must decide whether the edit serves the user's intent, protect motion that should remain stable with `preserve`, and preview the exact candidate on the target rig. The candidate fingerprint remains the commit token; audit settings do not change animation content.

Optionally add up to 16 `preserve` regions to the same request. The default composed guard is `{joint, startTime, endTime, sampleRateHz?, positionTolerance?, rotationToleranceDegrees?}` and compares the evaluated local pose from the base track, enabled layers in stack order, and root-motion contribution. `sampleRateHz` is 30, 60, 120 (default), or 240 uniform samples per second. Every authored key and quarter-point of each overlapping key segment is also sampled. To protect one authored channel instead, use `{joint, scope:"track", layerId?, startTime, endTime, ...}`; omit `layerId` to guard the base track. A track-scope guard verifies only that raw channel, not the full layered/composed pose. To protect a semantic phase across retiming, replace the absolute times with `{joint, phase:{label, occurrence?, startProgress?, endProgress?}, ...}`. Labels are `anticipation`, `main_action`, `follow_through`, and `recovery`; occurrence defaults to 1 and progress defaults to 0–1. Both source and candidate must contain the named phase or the guard fails closed. Each phase is resolved independently and evaluated at shared normalized within-phase progress, so different clip/phase durations do not shift the protected motion. The result includes both revisions' actual time bounds and peak-drift timestamps. `verificationMethod` distinguishes `exact_channel_match`, raw-track `sampled_track`, composed-pose `sampled_composed_pose`, and phase-aligned `sampled_normalized_phase_progress`. For example, `{joint:"LeftFoot", phase:{label:"recovery", startProgress:0.25, endProgress:0.9}}` protects 25–90% of the first recovery phase even if its boundaries move. A region requiring more than 8192 evaluations fails closed; narrow the interval or lower its sample rate. Defaults are 0.001 studs and 0.1 degrees. If either maximum exceeds its tolerance, the entire patch is rejected and no child is saved; successful previews and commits return measured drift. Use identical operations and preserve regions for dry-run and commit. Composed guards compare evaluated local joint transforms, not world-space skin deformation or rendered geometry; the finite sampling grid may still miss shorter deviations. Preview the complete candidate on the target rig as well.

- `set_pose`: replace position and/or rotation on an existing joint key. `time` must match the key within 0.0001 seconds.
- `mirror_pose`: copy a keyed transform from `sourceJoint` to `targetJoint`, using explicit `positionSigns` and `rotationSigns` (each component must be `-1` or `1`). It updates the matching target key or inserts an interior key when one is missing. Signs are local component rules, not rig-axis inference; preview mirrored work on the target rig, especially for custom joints.
- `mirror_tracks`: mirror 1–128 complete tracks using explicit `{sourceJoint, targetJoint, positionSigns, rotationSigns}` mappings. Supply both directions for a bilateral swap. The operation snapshots all source tracks before writing any target, so swaps cannot overwrite a source mid-operation. Duplicate targets and self-maps are rejected. Existing targets require `replaceExisting: true`; new targets are allowed within the 256-track limit. Key times, easing, and curves are preserved, and no joint mapping or axis signs are inferred.
- `transform_track`: apply component-wise position/rotation scales and offsets to every key in a joint track, preserving key times and easing. Set `sourceJoint` to copy/transform a different track into `joint`; if that target exists, explicit `replaceExisting: true` is required. Scale components are limited to -4..4. Offsets use local studs and XYZ Euler degrees. These are channel operations, not custom-axis or quaternion retargeting; visually verify on the rig.
- `insert_key`: add an interior breakdown on an existing joint track. Unspecified transform values sample the outgoing easing of the preceding key. Endpoint keys cannot be inserted.
- `set_easing`: change the easing style and/or direction on an existing key. The setting controls that joint's segment from this key to its next key; supported styles are `Linear`, `Constant`, `CubicV2`, `Bounce`, `Elastic`, and directions are `In`, `Out`, `InOut`. Omitted easing metadata in old recipes means `Linear`/`Out`.
- `retime_key`: move an interior key while keeping it strictly between its neighbors.
- `retime_clip`: change the clip duration and proportionally scale every base, layer, and root-motion key, contact boundary, and event marker. Pose values, easing, and layer settings are preserved. This operation is sequential: later operations in the same patch use the new duration and scaled key times.
- `retime_phase`: select existing `startMarker` and `endMarker` names (case-insensitive; repeated names use one-based `startOccurrence`/`endOccurrence`) and set the interval's `newDuration`. The start stays fixed, keys and markers within the phase scale proportionally, and all later times shift by the duration delta. Base, layer, root-motion, contact, and event timelines use the same map. The patch `changes` report returns piecewise source-to-candidate time-map segments plus counts of moved base/layer/root keys, contact intervals, and markers. A preflight rejects any base, layer, or root-motion track whose mapped key times cease to increase strictly, with the track and source/candidate times in the error. The clip's total duration must remain 0.1–30 seconds. Use `preserve` with a named phase to verify downstream motion survives the timing change; preview the candidate before commit.
- `adjust_phase`: reshape selected base or layer joint tracks inside named marker boundaries with `positionOffset` in local studs and `rotationOffset` composed in quaternion space. Fade envelopes default to 15% at each end and accept separate `fadeInProgress`/`fadeOutProgress` values from 0.01–0.5; the combined fades cannot overlap. Only interior keys with a non-zero envelope are changed, and every target track must already have keys matching both marker times (within 0.0001 seconds), so all boundary and out-of-phase keys stay exact. Repeated marker names use one-based occurrences. Direct overlap with a declared contact on the same effector is rejected unless `allowDeclaredContactOverlap:true`; when explicitly allowed, the change report lists it. This check cannot infer ancestor-chain effects or prove world-space contact, so rerun live contact acceptance tests and visually review the preview. Use `dryRun:true`, inspect the affected joints and `phaseAdjustment` report, optionally protect regions with `preserve`, then commit the exact candidate fingerprint.
- `delete_key`: remove an interior key. Start and end keys are protected.

All operations use recipe joint names and local transforms (studs and XYZ Euler degrees). Endpoint times are fixed, though endpoint poses can change if the finished recipe remains valid; loop clips must still have matching start/end poses. Joint tracks cannot be created by this tool. The finished recipe is validated for loop continuity, key ordering, duration and size limits before it is saved. If you need to add a new joint track, change clip duration, or make a broader rewrite, read the recipe and use `motion_library_save` with its `parentId` instead. Patches are sequential: each operation applies to the result of the previous operation, so later operation times refer to the already-edited recipe.

Roblox's native `Pose` easing direction labels are opposite the usual animation-editor convention for `In` and `Out`. Preview honors Roblox Pose semantics. Export adaptively samples nonlinear curves into extra linear keys (bounded by pose error and a 2048-frame export cap); `Constant` remains a native stepped segment. Inspect the saved animation in Studio for the final result.

### Inspection and feedback

`motion_review_start` takes `assetId`, optional `sessionId` and `rigId` together, `motionMode` (`unknown`, `in_place`, `root_motion`, or `stationary`), and `preview` (default true). It starts a background inspection and returns a review ID. It makes no provider API call unless `aiReview` is enabled with a configured `provider`. For a changed child, supply `compareReviewId` from the exact parent review that recorded the user change request.

For linked parent/child reviews, the child report includes normalized-progress and marker-defined phase comparisons when both versions have Studio samples from the same rig and matching joint hierarchy. Matching phase windows are aligned by label and occurrence, independently of their absolute timing, and expose parent/child times plus evidence IDs. Unmatched or missing phase windows are reported; they do not invalidate the overall trajectory comparison. This says where motion changed, not whether it improved; use the user request and visual review to interpret it.

Poll `motion_review_read` with `reviewId` until inspection finishes. The compact response includes measured findings, limitations, feedback questions, current review revision, and `visualEvidenceAudit`. Its `storyboard` groups only exact reviewed-recipe screenshots with the same rig topology, view, and focus, sorts their actual capture times, and reports sparse gaps. Manual images are kept in `referenceImages` with unverified caller time labels; stale recipe captures are excluded. The storyboard is a navigation aid, not proof of interpolation or what happened between frames. Set `includeSamples: true` only when examining actual sampled joint positions; this returns `telemetry` plus `poseEvidenceIndex`, which maps sample IDs to time/progress, coordinate-array slots to exact rig nodes/parents and optional driver class, inspector metric/finding IDs to their sample evidence, and authored-key/marker/contact moments to sampled or omitted coverage. `nodeSlotLimitation` states that a driver class does not establish local axes, anatomy, limits, or skinning. Use the index to interpret arrays rather than guessing node order; treat omitted moments as unobserved and request targeted evidence rather than inferring between samples. These measurements remain cues, not visual proof or automatic defects. Ask the user the questions and wait for their answers.

Studio pose inspection samples up to 128 distinct times. Contact boundaries and midpoints, evenly spaced poses, and up to 15 authored event markers are included within that budget; dense clips can still require a targeted follow-up review to inspect every event.

Finding `interpretation` is derived from cited evidence and validated again when reading persisted reviews. `excluded_evidence` is reserved for legacy findings that cite a known mismatched capture; new critiques cannot cite those images.

For linked child reviews, prior finding interpretation and screenshot identity are carried forward. A non-`uncertain` follow-up for a prior visual/reference or user-request finding requires a fresh screenshot bound to the exact child recipe; unbound references alone cannot establish that the child state addressed or retained the finding.

Use `motion_review_feedback` with `reviewId`, the current `revision`, and `feedback`: `overall` (`accept`, `refine`, or `redo`), `watchedPreview: true`, `liked`, `changes`, and `answers` containing `questionId` and `answer`. Only record feedback the user actually supplied. Acceptance requires no outstanding change request; refinement requires a description of what to change. Stale revisions are rejected. MCP feedback is labeled as reported by the client; the server cannot verify that a chat client asked its user.

Use `motion_review_critique` with the current review revision and configured provider after attaching any visual evidence. For linked child reviews, every carried-forward finding must be classified `addressed`, `still_present`, or `uncertain` using fresh evidence IDs. Each persisted finding includes a server-derived `interpretation`: `measured_issue` for pose-sample evidence, `observed_issue` for screenshots bound to the exact reviewed recipe, or `reference_target` if any cited image is an unbound user reference. An incompatible explicit model label is rejected; legacy findings receive a safe derived classification on read. A `reference_target` may guide motion toward a target, but it is not evidence that the reviewed animation already has that defect. An animation critique may include up to three evidence-cited patch proposals. Each proposal is either one localized pose/key edit (`set_pose`, `insert_key`, `set_easing`, `set_curve`, or `delete_key`) on one existing joint, or one coordinated `offset_pose_group` at a single time/layer across multiple exact joint tracks. The server derives the affected interpolation window and preservation intervals for each target rather than trusting guard locations generated by the model. It verifies unchanged composed motion on each edited joint outside its window and exact structural identity of all other recipe data. `motion_review_proposals_evaluate` includes this per-proposal preservation audit alongside live same-rig motion measurements, and the audit carries both exact source and candidate fingerprints. The preview returns the exact operation(s), derived intervals, per-joint affected windows, and preservation audit; pass the operations and returned guards unchanged to `motion_animation_patch` with `dryRun: true`, inspect the candidate, then commit only after explicit user approval using the same inputs and dry-run candidate fingerprint. If an edit spans a target joint's full affected timeline, no outside interval can be listed for that joint; the exact structural check for all other data still applies. Legacy proposals without server-derived guards fail closed. Proposals are never applied automatically. When multiple proposals are available and the matching live rig is connected, call `motion_review_proposals_evaluate` with the exact review revision and proposal IDs to sample the source once and each distinct candidate sequentially on that rig. Optionally provide explicit `acceptance` criteria (duration/loop, required markers/tracks, maximum angular speed, and contact requirements) to evaluate every candidate against the same caller-authored contract; omitted thresholds are never invented. It returns each candidate's structural audit, Studio inspection, normalized-timeline change map, declared-contact trend matched by effector/kind/exact interval, optional per-check passed/failed/unknown results, and candidate fingerprint; a changed contact window is unknown rather than incorrectly paired, and no winner is selected. Screenshot follow-up distinguishes `matched_frames_ready` (same-recipe capture) from `reference_only` (unbound user target image): the latter can guide a target comparison but is not a before-state and cannot alone establish that a reviewed defect was fixed. Unsupported views/times or incompatible joint maps require manual matching. Read the resulting review again; AI findings and proposals are not acceptance.

`motion_studio_capture_views` takes a required `sessionId`, `rigId`, and animation `assetId`, plus 2–8 unique `{view,time}` pairs. Its successful job result validates every frame against the exact saved recipe fingerprint, rig/topology, and ordered requested schedule, then reports explicit complete/partial `captureCoverage` and missing pairs. This indicates capture metadata coverage, not AI image inspection. It returns frames with a `captureId`, recipe fingerprint, rig ID and topology signature, time/view, byte length, chunk count, and dimensions. First pass all returned IDs to `motion_studio_read_candidate_captures` and inspect the image blocks as the calling agent; this verifies and returns the actual rendered PNGs as a single bounded response. Each read result includes a strict-schema `reviewCapture` projection beside its enriched metadata. Pass those `reviewCapture` objects—not the expanded metadata objects—to `motion_review_attach_captures` with the current review revision. When present, joint-mapping provenance is retained through review persistence and shown to both the later image reader and critique provider; a mapped screenshot remains labeled as name-only evidence after the temporary capture expires. The local review server verifies exact recipe and rig/topology binding, chunk metadata, PNG structure, and actual IHDR dimensions before fingerprinting and attaching each image. Retrying the same `captureId` with identical metadata is idempotent, even if the successful response was lost; reusing it with changed metadata is rejected. On a later reconnect, `motion_review_read_images` returns 1–8 persisted screenshots as checksum-verified image blocks with per-image metadata and citation guidance; it fails closed without returning a partial set if any requested file is missing/tampered or the byte budget is insufficient. Native Studio screenshot support remains runtime-dependent. If it fails, attach a manually captured image instead; manual images do not qualify for fingerprint-bound planned capture coverage.

Use `motion_review_attach_manual_image` when you have a user-provided PNG and native Studio capture is unsupported, unavailable, or denied. It reads an explicit absolute local path, persists the PNG into the local review, and advances the review revision. The supplied view/time are user labels only; the image has no Studio capture ID, recipe fingerprint, or rig binding, so it is categorized as `unbound_user_image` and may serve only as a reference target. It never satisfies planned native capture coverage or proves the reviewed animation currently has the pictured pose. The response now includes current `visualCaptureCoverage`, `visualEvidenceAudit`, and a branch-specific `next` handoff: planned reviews remain blocked on missing fingerprint/rig-bound frames, while unplanned reviews are directed to inspect the actual PNG and keep any critique reference-only. `motion_studio_capture_candidate_views` accepts a complete inline animation recipe and either 2–8 explicit camera/time pairs or no frames, in which case it creates a bounded plan from phases, contacts, markers and measured motion peaks. Omit frames to avoid a separate planning call; tune the automatic plan with `views` and `maxFrames` (defaults: front/side and eight total images). The plan is returned with the successful `motion_studio_job` result and should be reviewed before inspecting the images. If a separate plan was reviewed, pass its candidate fingerprint as `expectedFingerprint` to bind capture to that exact recipe. Capture evaluates the temporary preview against the selected rig, returns short-lived capture metadata, and does not save the animation or authorize export. It can apply an explicit name-only `jointMap` for screenshot posing even when recipe names fail the exact-name viewport-open gate; the returned `jointMapping` reports the map fingerprint and number of renamed joints. This is useful for approximate visual inspection, not true retargeting: local axes are unchanged, IK is not solved, and semantic equivalence is not established. Retrieve rendered PNGs with `motion_studio_read_candidate_captures` in one response (1–8 images, including a lone frame from a partial capture) or `motion_studio_read_candidate_capture` individually. The same readers support saved-animation, candidate-comparison, and exact editor-draft captures. The batch reader returns no images unless all requested chunks verify and the aggregate byte budget is met; on failure it supplies a bounded per-capture read plan. Image bytes are assembled and checked against the PNG chunk structure and actual IHDR dimensions locally, then returned as MCP image content bound to capture ID, fingerprint, rig, time, view, and mapping provenance. Captures expire after 180 seconds or cache eviction. The same live Studio session and selected rig are required to retrieve them. Native screenshot permission/runtime support is still experimental and must be verified in Studio; these pixels are evidence for visual judgment, not an automatic quality verdict.

For unsaved recipes, `motion_studio_capture_candidate_plan` applies the same deterministic moment planner as saved-clip review. It returns the exact candidate fingerprint, selected `{time,view}` pairs, reasons for each chosen moment, and a bounded `omittedMomentSummary` with the total number of unselected moments plus up to twelve highest-priority examples and their reasons. The planner uses phase-composed local-pose extrema and excludes disabled/zero-weight layer peaks, in addition to authored phase, contact, marker, and active-channel evidence. When interior budget permits, it spreads motion-peak review across distinct moving joints before falling back to generic uniform samples; a shared timestamp can cover several joints. The eight-frame budget is shared across requested views: front+side permits up to four shared moments, while four angles can leave only start/end poses per angle and miss the action. Prefer front+side for temporal review, inspect the omitted summary, and explicitly request any important omitted beat; add views only when their spatial evidence is worth fewer moments per angle. Authored times and clip endpoints retain their exact recipe precision; the planner does not silently quantize nearby beats into one timestamp. It returns `jointMapFingerprint` too: pass it as `expectedJointMapFingerprint` with the unchanged recipe, exact joint map, and frames to `motion_studio_capture_candidate_views`. Do not save a draft just to plan its visual review. The planner is advisory and does not infer artistic intent or guarantee that selected frames expose every issue.

For side-by-side alternatives, call `motion_studio_capture_candidate_comparison_plan` with 2–4 distinct, equal-duration animation recipes, requested views, and a 2–4 frame budget. It keeps clip endpoints, then balances candidate-specific phase/contact/marker/peak moments into one matched timestamp set and explains which candidate contributed each reason. Candidate-exclusive authored contacts and markers outrank generic phase-composed pose extrema when selecting limited interior slots, protecting unique evidence from being crowded out by redundant pose peaks. Its `candidateCoverage` reports how many unique moments from each recipe are represented by the shared schedule, how many are omitted, and up to twelve omitted examples; when beats must be omitted, candidate-exclusive authored contacts and markers appear before raw-priority peaks in those examples too. Use these to decide whether to explicitly capture an important beat outside the shared comparison. Its `timingAlignment` also compares loop mode and same-named markers/contact windows in normalized clip progress; `timing_variants` and `semantic_mismatch` warn that an identical timestamp may show different semantic beats, so avoid attributing a timing change to pose/style quality. On success, `motion_studio_job` returns image metadata grouped by candidate label; `motion_studio_read_candidate_comparison` returns those PNGs as labeled image blocks in one response, subject to its aggregate byte budget. These sparse storyboards help the agent compare visible pose progression without implying continuous playback. Still-frame sequences cannot establish interpolation, velocity, smoothness, or events between sampled times. If the response budget is too small or any image chunk fails verification, the grouped reader returns no image blocks and provides a bounded `readPlan` with capture IDs, labels, times, and views for individual retry or a larger bundle limit; do not claim visual inspection until actual PNGs are returned and inspected. Optionally pass the user's explicit success criteria; the response includes a guidance protocol to assess every candidate against them, cite capture IDs, and mark unobservable criteria unclear. For a recheck, supply `expectedRigSignature` returned by `motion_studio_visual_bakeoff_recheck_plan`; a mismatch is rejected before queuing capture. Use `motion_studio_read_candidate_capture` for a single image or when the bundle exceeds that budget. If one capture fails, the result identifies the failed alternative/frame and preserves available images; grouped reading refuses partial results unless `includePartial=true`. The workflow never ranks, saves, or approves a winner. This is evidence-gathering, not a substitute for human judgment or a visual-quality score.

`motion_studio_visual_bakeoff_recheck_plan` takes a prior `historyRecordId` and the current candidate recipes. Matching labels are not proof of semantic equivalence; use them only as an intentional mapping. Capture all new screenshots and re-assess every candidate—prior image citations cannot count as new evidence. Pass the returned `baseline.rigSignature` as `expectedRigSignature` to the capture tool, then pass the returned criteria to the image reader and report validator. Persist the new report and compare its ID with the old one. Different rig topology cannot be treated as an apples-to-apples visual recheck.

After inspecting all images, `motion_studio_validate_candidate_comparison_review` requires exactly one finding for each candidate/criterion pair and verifies citations belong to retrieved captures of that candidate. A valid report is saved append-only under `artifacts/visual-bakeoff-runs/` with exact candidate fingerprints, candidate durations, cited image hashes, each citation's normalized clip progress, and compact deterministic audit snapshots of each exact recipe. Cited PNG bytes are stored separately by SHA-256; report metadata binds each image to its candidate fingerprint, capture, timestamp, view, and digest. `motion_studio_visual_bakeoff_evidence_image_read` returns one image only after rechecking its byte count, SHA-256, and PNG dimensions. Older reports without persisted images remain readable. Historical screenshots are not fresh evidence of a revision, and agent observations remain unverified. Exact recipe contents are stored separately in immutable, content-addressed local snapshots and checked against their candidate fingerprints. New report records attest that the full recipe snapshot set was persisted; history reads verify every attested snapshot and fail closed on missing or corrupted data. Use `motion_studio_visual_bakeoff_recipe_read` with a history record ID and candidate label to recover the precise unsaved candidate after server restart for further AI refinement; recovery does not save it to Roblox. Use `motion_studio_visual_bakeoff_history` and `motion_studio_visual_bakeoff_read` to recover reports, then `motion_studio_visual_bakeoff_compare` to compare report structure, cited evidence times, and audit snapshots on the same rig topology. Audit comparisons include raw before/after recipe counts, local peak speed/acceleration and loop-seam deltas, and structural advisory additions/removals. They are offline local-channel recipe measurements—not rendered, physics, or quality evidence—and numeric direction is not classified as better or worse. The comparison includes a `regressionSummary` with coverage completeness and status transitions; “reported_regressed”/“reported_resolved” describe only agent-authored labels. Per-candidate summaries show recipe identity changes, status distributions, reported transitions, citation counts, criterion coverage and inspected views. Recipe edits remain comparable by the intentional candidate label but are explicitly marked; matching labels do not establish semantic equivalence. Any changed rubric/candidate set or unclear assessment makes the summary inconclusive. This is not a verified quality gate: inspect fresh images and test the animation in gameplay. Evidence-time comparison aligns by candidate label, criterion, and view, and reports normalized-progress deltas when counts match. This compares which images the agent cited, not when the underlying motion event occurred; it cannot tell whether a changed note means the motion improved. Older reports without duration, audit snapshots, or recipe snapshots remain readable and report unavailable normalized progress/technical audit/recipe as applicable. Agent-authored visual interpretations remain unverified.

To continue a refinement after reconnect or server restart, call `motion_studio_visual_bakeoff_refinement_context` with the history record ID and candidate label (optionally one criterion). It returns the exact verified recipe and source fingerprint together with finding metadata and a ready `patchPreviewBinding` for any contradicted finding. Each cited historical frame is supplemented with recipe-derived normalized progress, nearby authored markers, active declared contacts, and nearby contact boundaries. This context is reconstructed from the fingerprint-verified recipe, but does not validate the original observation or prove actual contact. Retrieve cited historical PNGs with `motion_studio_visual_bakeoff_evidence_image_read` and inspect them as context; they are not fresh evidence of a revision. Pass the binding, recipe/fingerprint, explicit `changeIntent`, and reviewed patch operations to `motion_animation_candidate_patch_preview`. The server checks persistent report integrity, candidate identity, criterion status and exact evidence citations before returning a preview-only patch. Re-capture the revised candidate for fresh visual review before committing or saving it.

To get measured technical evidence before saving a recheck, call `motion_studio_visual_bakeoff_candidate_recheck` with the same history ID/label and the revised unsaved recipe (for example, the candidate returned by patch preview), plus the connected session/active rig. It recovers the exact baseline snapshot and refuses to compare if the current rig topology signature differs from the persisted bake-off baseline. It samples baseline then revision sequentially on that topology and appends an integrity-checked record with the exact baseline/revision fingerprints, sampling settings, and both raw Studio telemetry snapshots; the revised recipe is stored by content hash. The telemetry asset IDs must be the deterministic identities derived from those exact recipe fingerprints, preventing otherwise well-formed telemetry from being relabeled as a different candidate. The response includes the record ID, both structural audits and Studio inspections, normalized-progress pose/contact changes, and optional explicit acceptance checks for both. It neither saves either animation to Roblox nor chooses a winner. Use `motion_studio_visual_bakeoff_candidate_recheck_read` to recover and recompute a run after reconnect, `...candidate_recheck_history` to list runs (optionally filtered to a parent report), and `...candidate_recheck_compare` to compare only records sharing the exact parent candidate baseline, rig identity, and topology. Reads verify the parent report and both recipe fingerprints before recomputing results from stored telemetry; record corruption or missing snapshots fail closed. These samples are fresh mechanical comparisons—not replayed screenshots or gameplay physics. Capture fresh views after each run before assessing whether the visual issue was resolved.

After the user approves that exact preview, `motion_animation_candidate_patch_commit` reapplies the operations and requires the exact `candidateFingerprint` returned by the preview. Exact retries after a lost response reuse the same deterministic asset identity; changed provenance cannot silently reuse the old record. Optionally pass `parentAssetId` only when it contains the exact source recipe; the server verifies this before saving. The immutable library asset stores patch operations, preservation guards, change intent, and any validated persistent visual finding, and revalidates their fingerprints when read. Retrieve the full lineage with `motion_library_read`; paginated listings remain metadata-only. It still does not save to Roblox Studio; export remains a separate preflighted operation.

After inspecting the returned images, `motion_studio_validate_candidate_comparison_review` checks that an agent-authored report covers every candidate/criterion pair, uses the same rubric that accompanied the images, and cites only images actually retrieved for that candidate. The server does not verify visual claims, choose a winner, or accept any animation; this structured handoff is still ephemeral and is not a quality certificate.

For a multi-view result, `motion_review_attach_captures` accepts 1–8 frame metadata objects and handles revision increments internally. For a revised MCP-authored recipe, call `motion_library_save` with the reviewed asset's `parentId`, then inspect the new ID. The local browser panel also offers provider-powered generation directly from a saved feedback record. See [the review guide](animation-review.md) for evidence limits and storage.

### Format

Each track has a joint name and at least two keys spanning zero through the animation's duration. A key contains:

- `time`: seconds
- `position`: local XYZ offset
- `rotation`: local XYZ Euler angles in degrees

Interpolation is linear. A looping clip must end at its starting pose. Markers such as `Release` are preserved. See [custom-idle.json](../examples/custom-idle.json) for a complete recipe.

Use `motion_animation_suggest_joint_map` with the saved animation and either both `retargetProfile` objects returned by `motion_studio_inspect`, or `sessionId`, `sourceRigId` and `targetRigId` to load recent successful inspections directly from the live plugin session. Inspect both rigs first; select the target rig before asking for the report. Session-cached profiles are limited to five minutes, and the active target signature must still match. The advisor returns ranked candidates with evidence and only includes distinct, strong heuristic matches in `suggestedJointMap`; its confidence values are not calibrated probabilities or proof of anatomical correctness. Ambiguous names, parent conflicts and collisions must be resolved explicitly. Suggestions are read-only and are never applied automatically. Inspect the result, then pass the confirmed map to `motion_animation_retarget`. Motor6D animation targets use **Part1 names**, not the names of the Motor6D instances. Bone animation targets use bone names. Mapping names does not retarget local axes or rest poses.

Studio saves use the rig's `AnimSaves` reference and a folder in ServerStorage, or an existing legacy AnimSaves folder. This follows Roblox's [local animation save model](https://create.roblox.com/docs/animation/editor). Loading these generated clips in the native editor still needs verification.

## Blender

The worker reads a saved `.blend` file in a separate Blender process. It does not see unsaved changes in an open window. Each authoring operation writes a new `.blend` and returns `blendFile`. Use that path for the next operation. Outputs and logs are stored in `artifacts/blender/`.

Humanoid fitting assumes a Z-up T-pose and uses the mesh's bounding box to place a rough guide. Supply world-space landmarks to improve the fit. A-pose characters, creatures, clothing, and unusual proportions need more work. Inspect shoulders, elbows, hips, and knees even when the numeric weight checks pass.

Use `bind: false` to create just the armature. Automatic binding keeps the four strongest deform influences per vertex and normalizes them. FBX export rejects unweighted vertices or invalid influence counts. Familiar Roblox bone names do not by themselves make a model a valid R15 avatar or Marketplace asset.

Direct animation rejects active constraints on targeted bones. Bake or disable them in a copy first. Existing NLA tracks are muted in the output so they do not override the new action. Export includes the armature, bound meshes, and one active animation clip. Check scale and motion in Roblox's importer.

## VFX

Effects use native ParticleEmitters. Custom textures must be Roblox asset IDs you can access. The starter texture requires no upload. Saved emitters start disabled; their `EmitCount` attribute stores the burst count. See [custom-spark.json](../examples/custom-spark.json) for an example.

A VFX recipe can instead include `"column": { "length": 18, "travelTime": 0.35, "fadeTime": 0.25, "origin": "hands" }`. This creates a growing 3D cylinder with a rounded leading edge, arrival flash, and fade. `size` is its diameter and `lifetime` includes travel, hold, and fade. Lifetime must exceed travelTime plus fadeTime. Origin defaults to `attachment`; `hands` requires R15 LeftHand, RightHand, and HumanoidRootPart and follows the hand midpoint along the root's forward direction. Column and beam modes are mutually exclusive. Saved columns contain a `MotionColumnRecipe` attribute for replay; they do not install gameplay scripts or damage logic.

## Experimental review capture

Before planning image-based review, optionally call `motion_studio_capture_preflight` with the connected `sessionId` and active `rigId`. Studio checks whether `StudioCaptureService` exists, requests screenshot permission, and checks `CanCaptureScreenshot()` plus viewport dimensions. The permission request may prompt the user. It does not move the camera, create a preview, or take an image. The plugin rechecks rig identity/topology after the permission request, and the MCP server validates the returned session/rig binding and current topology before showing the result. `ready` is momentary evidence only; capture may still fail later. The returned `next` is status-specific: `unsupported` means stop retrying this native API; `permission_denied` means do not ask again unless the user chooses to change permission; `temporarily_unavailable` may be retried only after Studio/viewport availability changes; and `unknown` calls for inspecting the error and restoring/reconnecting the plugin before another preflight. Until a ready preflight and inspected PNGs exist, continue technical pose/rig checks but do not claim AI rendered review. A user-provided screenshot can be inspected as unbound reference evidence only; it cannot prove the exact fingerprint-bound candidate was captured.

Call `motion_studio_capture_plan` with an animation assetId to propose a bounded schedule. It selects clip endpoints, named phase boundaries, contact start/mid/end moments, measured motion peaks, and authored markers, with category diversity when the frame budget is tight. Optionally pass exact `focusJoints` from `motion_studio_inspect`; if authored names differ from inspected rig names, supply `jointMap` and reuse the returned map in capture. Active base tracks, enabled nonzero-weight layer tracks, and root-motion channels can receive close-ups after this mapping. The planner preserves at least two whole-rig moments per requested view, favors matching authored joint keys, and reports `focusJointCoverage.omittedDetails` with the reason for each unscheduled close-up. A target must still exist as a part-backed node in the active Studio rig. It returns the exact `animationFingerprint`, selected times and reasons. The schedule is deterministic, but it does not know which side best shows a silhouette or whether a peak matters artistically.

Single-animation plans (saved animation, unsaved candidate, and automatic editor-draft capture) can receive up to 31 exact `priorityTimes` from a user brief or validated analysis. Supply them in importance order; the planner schedules as many as the view/frame budget allows before optional close-ups and ordinary cues, and returns `priorityTimeCoverage` with requested, scheduled, and omitted times in that order. Blueprint previews expose every distinct internal phase start, midpoint, and end with its associated intent; order those exact times by importance instead of taking the first six chronologically. A single front-view plan with `maxFrames: 8` can show up to six interior beats. For omissions, the planner returns exact, ready-to-send `priorityTimeCoverage.followUpBatches` arrays (each preserves the requested views and has at most eight frames); pass each unchanged as `frames` in a separate capture call with the original recipe and identity guards. When the planner chooses its own interior motion cues, it favors distinct moving joints before generic uniform samples if the budget allows. Do not pass `priorityTimes` alongside explicit `frames`.

For automatic editor-draft capture, pass `priorityTimes` with the exact unsaved recipe when you want selected intent beats reserved in the initial frame budget. If the job returns omitted-time follow-up batches, its `next` instructs how to resubmit each exact array with the same editor asset, draft recipe/fingerprint, loaded-source fingerprint when available, joint map, joint-map fingerprint, and rig signature. Explicit `frames` and `priorityTimes` are mutually exclusive; retrieve and inspect each retry's images before calling those beats visually reviewed.

Pass the plan's `frames` to `motion_review_start` as `plannedCaptureFrames` to bind the expected view/time pairs to that review. `motion_review_read` then reports `visualCaptureCoverage`; each evidence image can satisfy at most one planned pair, and missing pairs are listed. `motion_review_critique` refuses to run until every planned pair has an attached image. Coverage verifies metadata only—not that Studio rendered the intended pose, that the camera framing is useful, or that the image supports a quality claim. Without `plannedCaptureFrames`, the existing flexible manual/partial-image review workflow is unchanged.

When the reviewed animation has persisted blueprint `authoringIntent`, `motion_review_critique` includes it as an original creative brief for bounded proposal generation. It also supplies `timingMatchesCurrentRecipe`; only when true do the brief's normalized boundaries identify the current recipe's timing. `motion_review_proposal_preview` returns the same brief and match status so the caller can consider intent alongside its linked finding, cited evidence, and exact patch. The brief is never screenshot evidence, a quality verdict, or proof that a proposed edit improves the animation.

After `motion_review_read` lists an attached screenshot's image ID, call `motion_review_read_image` with that `reviewId` and `imageId` to return its actual PNG as MCP image content. The tool verifies that the image belongs to the review and its bytes still match the stored SHA-256 before returning it. Identity guidance is returned immediately before the PNG: `matches_reviewed_recipe` means the capture is bound to the exact reviewed recipe, `unbound_user_image` is reference only and does not prove the reviewed pose, and `mismatched_reviewed_recipe` is ineligible to guide critique or edits. The batch reader includes the same classification in each image's `visualReviewTemplate`. Successful retrieval proves integrity and association only, not that the image depicts the requested pose or supports a visual claim. Cite the image ID in any critique and distinguish visible evidence from inference.

Every new screenshot critique must classify each supplied image as `observed` or `inconclusive` in `visualObservations`. Use `inconclusive` when a pose or relevant detail is occluded, too small, ambiguous, or otherwise not reliably visible; the server rejects visual findings that cite an inconclusive image and rejects non-`uncertain` child follow-ups based on one. The provider also receives `pixelSignal` diagnostics for extreme uniformity/transparency: warnings are a legibility cue, never a quality verdict, and no warnings do not prove visibility. Signals are persisted with image metadata and included in `motion_review_read.visualEvidenceAudit.images[]`, proposal cited-image evidence, and revision visual context; legacy images without stored signals are reported as unavailable there. Persisted reviews are checked against the same evidence rule. `motion_review_read.visualEvidenceAudit.images[].visualAssessment` exposes the disposition, with `legacy_unclassified` for older critique records that predate this field. This readability classification is separate from whether a user-intent criterion is supported, contradicted, or unclear.

`motion_studio_capture_frame` takes rigId, assetId, jointMap, time (0-10 seconds), and view (`front` or `side`). It stages the animation pose on a disposable clone, temporarily controls the camera, and requests a UI-free 960x540 PNG. Native screenshot permission is required. It restores the camera and removes the clone after the capture attempt without stopping the user's shared interactive preview. If the user changes the camera while capture is waiting, it preserves that new view and restores Studio camera control. Both native capture tools bind returned metadata to the exact recipe fingerprint and live rig topology signature; the plugin rechecks topology during capture. `motion_studio_capture_views` accepts 2–8 named view/time pairs; pass the capture plan's frames and `animationFingerprint` as `expectedFingerprint` so a changed recipe is rejected before capture is queued.

`motion_studio_read_candidate_captures` reports strict per-batch `sequenceGroups` and separate `temporalContinuityGroups`. The latter can combine timestamps from separate capture batches only when source, exact recipe fingerprint, rig topology, actually applied joint mapping, IK target-guide candidate, view/focus, and editor-draft identity all match; each frame keeps its `captureBatchId`, and duplicate timestamps count once for temporal spacing. Use this to place a later targeted capture alongside compatible earlier frames. It remains sparse still evidence, not proof of interpolation or continuous motion; its largest-gap midpoint is only an optional next capture time.

Retrieve the returned captureId with `motion_studio_capture_chunk`, supplying zero-based index. Each result contains at most 32768 bytes encoded as hex, below the existing bridge message limit. A local client should decode chunks into a PNG rather than feed hex to a model. The latest capture replaces the previous one and expires after 180 seconds; maximum file size is 2 MB. This bounded chunk transport is the pilot alternative to adding a new binary HTTP route. No image is sent to an AI provider automatically. Runtime availability, camera restoration, image framing, and PNG decoding remain pilot checks.

For a continuous laser, add `"beam": { "length": 15 }` to a VFX recipe. This replaces the emitter with a colored Beam and a pale core, pointing along the parent part's local -Z axis. `offset` positions the start, `size` controls width, and `lifetime` controls preview duration. Length is limited to 100 studs. Particle-only settings are ignored in this mode. Saved beams start disabled; their parent attachment has a `Duration` attribute. Enable both Beam children for that duration when triggering them in gameplay. No collision or damage is added.

Preview cues fire once at the requested times. Continuous emitters run until cleanup. Looping the animation does not repeat the cues. The tool does not add gameplay scripts to trigger saved effects.

Animation preview evaluates joints directly on an anchored clone. Confirm final runtime behavior in the game after publishing.

## Studio test checklist

These checks remain to be run in the native application:

- Connect the plugin and inspect a selected R15 rig.
- Preview idle and cast recipes. Confirm the original rig stays unchanged.
- Preview VFX on a hand. Stop the preview and confirm its clone and effects disappear.
- Save a sequence and load it through the Animation Editor's animation list.
- Save a VFX attachment, then use Undo. Confirm only that operation is undone.
- Disconnect Studio before a queued command is delivered. Confirm it expires without running later.

For weights-only `motion_animation_graph_timeline_simulate` calls, set `includePoseSamples: false`. This skips per-joint local pose composition but retains `blendSamples`, including requested exact track-weight timestamps. Do not pass `poseJoints` in this mode. Pose composition remains enabled by default when `sampleTimes` is requested.

For natural completion timing, `motion_animation_graph_timeline_simulate` and each `motion_animation_graph_timeline_test` case accept optional `naturalCompletionFadeSeconds`. This explicitly models a caller-supplied fade after a non-looping clip's authored end: the track stops playing and begins fading at clip end, then `AnimationEnded` is delivered when the fade interval completes. It defaults to zero for compatibility; the report labels this as an assumption, not a Studio-measured value and not a value inferred from `Stop()` fade calibration. Validate any supplied duration against the target rig and Studio build.

When an exact, fingerprint-verified, unambiguous natural-completion profile exists at the active playback speed, the simulator uses its observed `AnimationTrack.Length` for the non-looping clip playback clock—even if that measured length differs from the authored recipe duration. The mismatch is reported. A mismatched profile does not authorize its measured natural-fade duration or `WeightCurrent` curve: additional fade defaults to zero unless supplied explicitly, and measured natural-fade curves are used only when measured length matches the recipe within one sample interval. Ambiguous or missing evidence falls back to authored duration. This is empirical calibration for the captured Studio rig/build, not a guarantee about other assets or live gameplay.

Generated graph controllers expose `SetPlaybackSpeed(multiplier)` and `GetPlaybackSpeed()`. The multiplier is bounded to `0.1–4`, scales the current state's playback rate (including every active BlendSpace source) without changing relative phase rates, and persists across state transitions. Speed changes are applied to every active source track as one operation; on a Roblox `AdjustSpeed` failure, the runtime attempts to restore all tracks and returns attempted/restored source IDs plus rollback failures. `Controller.BindToPlayer` forwards both methods to the current character controller.

Timeline simulation events also accept `{ at, kind: "set_playback_speed", multiplier }`. A speed change preserves active normalized phases, scales all active BlendSpace source clocks by the same ratio, and reschedules future markers and non-looping completion callbacks from the new speed; old callback generations become stale. The report returns `finalPlaybackSpeedMultiplier`. This is a deterministic timing estimate and does not execute Roblox's frame scheduler or guarantee exact callback delivery timing.

When `analyzeEventOrderSensitivity` is enabled, the simulator compares blend samples and composed poses between user-first and runtime-callback-first runs in addition to state, parameter, marker, and timeline outcomes. Event times are rounded to 12 decimal places only when the correction is within a floating-point-scale tolerance (twice machine epsilon times the larger timestamp magnitude), preventing phase-to-seconds roundoff from hiding a genuine tie (for example, `0.0619` becoming `0.06189999999999999`) without collapsing distinct authored events separated by more than representational noise. For event-generated observations, the normalized time snaps to the nearest existing explicit or uniform sample within that same tolerance (ties choose the earlier timestamp); otherwise it adds one normalized timestamp. This removes duplicate observations for an event on a frame while preserving the existing explicit/frame timestamp and keeping distinct explicit requests separate. Times beyond the requested simulation horizon retain their original values and are not rounded into the run. Blend and pose values are compared at timestamps present in both runs, avoiding false output divergence when callback cancellation causes one policy to have extra observation timestamps. The optional `maxEventOrderDivergences` gate counts up to seven outcome dimensions and fails closed if either policy has sample timestamps the other did not compare. This prevents incomplete evidence from passing a regression gate while still avoiding false sample-value differences at non-shared timestamps. The comparison remains between two deterministic policies and does not predict Roblox callback ordering.

### Rig-bound blueprint scale cues
motion_animation_blueprint_preview returns each authored joint's largest local position offset from neutral and largest positional change between consecutive keys (time window, vector, magnitude, and ratio to the inspected segment length). The latter is key-to-key displacement, not interpolated path length or velocity. Ratios are scale context only—not anatomical/physical limits, axes, collision results, clamps, quality scores, or pass/fail thresholds. Use live rig evaluation and viewport review to judge the animation.


For blueprint drafts, inspect the returned `structural.curveMotion` and `structural.actionPhaseMap.poseProgression`/`peakEvents` before live visual review. These easing-aware local-curve speed/acceleration/jerk cues and key-segment locations can focus review, but they are not defects, rig-space/world-space motion, or artistic quality judgments.

When a generated animation draft was bound to a freshly inspected rig, its completed authoring job and `artifacts/generations/<assetId>.json` provenance include the same derived `rigCoverage` snapshot. `channelCoverage` reports exact authored, active, inactive-only, unresolved and intentionally un-authored driven joints; `semanticRoleCoverage` summarizes recognized R6/R15 or cautious custom-name roles and any shared aliases. `nextActions` uses stable codes to identify unresolved authored names that need exact rig resolution and disabled/zero-weight layer channels that merit review. It never applies a map or enables a layer. A role with no authored channel is not a failure or a quota—the action may intentionally leave that body area still. This is structural coverage context, not rendered evidence or an artistic-quality verdict. VFX drafts and animation drafts generated without a validated rig do not include this field.

Every generated animation draft also includes a compact deterministic `motionAudit` in its completed job and generation provenance, whether or not a rig was inspected. It contains the recipe summary, structural advisories, up to four ranked local-curve refinement cues, and an omitted-cue count; it is a review aid, not an automatic rejection or quality score. Use `motion_animation_audit` for the full structural report, then evaluate and preview the exact candidate on the target rig. Numerical cues do not establish world-space movement, contact, visual quality, or approval. VFX drafts omit this animation-only field.
On a rig-bound blueprint, motion-audit channel joints and rig guides share exact names. Correlate `target.joint` with `rigValidation.jointPoseGuides[].joint` to inspect its parent and measured segment length when reviewing a peak; do not infer world-space travel or anatomical limits from local channel values.
For unfamiliar/custom joints during blueprint authoring, selectively call `motion_studio_probe_joint_axes` when local response direction is uncertain; do not probe every standard joint by default. Its detached-clone finite differences are local to the zero-input baseline and are not anatomy or joint limits.

In `motion_studio_read_candidate_captures`, `temporalSampling.largestGapInterval` identifies the exact adjacent capture IDs, timestamps, and normalized-progress endpoints around the widest unobserved interval. Its `suggestedTime` is the arithmetic midpoint for an optional recapture in the same view/focus; use the exact same source recipe and the normal preflight/permission flow. It is advisory, never captures automatically, and locates an evidence blind spot without inferring the unseen motion.

For auto-planned candidate captures, the short-lived capture record also retains the exact recipe-bound plan. The grouped image reader compares each whole-rig view with that plan and reports `plannedMomentOmissions` plus exact-time `recaptureSuggestions` for unsampled authored beats in that view; it excludes moments already present in the view and does not attach this advice to focused close-ups. Omission summaries reserve bounded samples for distinct cue categories (including authored markers) before filling remaining slots by planner priority, so a dense set of measured peaks cannot hide every missed event from the AI. These reasons are planner cues, not defects; the AI should request only relevant stills through the ordinary preflight/permission flow. Neither the plan nor the sparse images prove continuous motion or image quality.

Animation graph temporal pose expectations may set `missingBlendChannels` to the exact `{controllerStateId, sourceStateId}` pairs expected to have positive current pose weight but no authored channel for that joint. Use `[]` to assert complete channel coverage. A mismatch fails the pose check and includes each observed source's priority, current/target weight, and playback time in its diagnosis. This gates authored channel coverage only; it does not substitute for live rendered review.

For a source that should have the joint channel, `poses[].blendSourcePoses` can assert its final joint `effectiveWeight` range and/or sampled local position and rotation at the exact pose timestamp, independently of the final composed pose. Add `throughout` to require source coverage and gate its effective-weight range, sample gap, linear/angular speed, or per-sample step across a window. The suite samples authored key/easing extrema and graph-transition boundaries in addition to the requested uniform rate; every requested time must have the named source contributing that joint. Effective weight is after track-priority masking, distinct from normalized BlendSpace weight. Positions are local recipe studs; rotations are local XYZ Euler degrees compared with quaternion angular distance. Failed checks report the sampled source transform, contribution status, and current weight; an absent contribution distinguishes a missing authored joint channel (including source weight and playback time) from a source that simply is not contributing. `timeline_plan_preview` summarizes these in `coveragePreview.poseCoverage.blendSourcePoseAssertions` and `blendSourceThroughoutWindows`. It also returns `sourceReferenceAssertions` (controller/source validity and whether that source animates the asserted joint) and `blendSourceCoverage` (enabled exact-time checks, the uniform throughout-window sample count, active range/gap/speed/step gates, and the fact that runtime critical times are added). Top-level `coveragePreview.valid` is false and `coveragePreview.blockers` identifies each invalid source assertion with a stable `reason` and a `recommendedAction`; correct them before creating a plan. Reasons distinguish a non-BlendSpace controller, a source not in its controller, a required joint channel that is absent, and a missing-channel assertion contradicted by an authored channel. A source-pose assertion requires an authored channel in the referenced state (base, enabled nonzero-weight layer, or root-motion channel); use `missingBlendChannels` when asserting an expected absence. Creation and run revalidate source references and channel expectations against pinned recipes, including idempotent retries. If plan creation is blocked by one of these assertions, its error repeats the first preview blocker’s stable reason and recommended action; a stale or mismatched preview fingerprint is still rejected first. Uniform counts exclude authored-key, easing-extrema, and transition-boundary samples. Suite fingerprints bind the exact targets. This is an explicit authored-pose regression gate, not a rendered or artistic-quality judgment.

When `studioCalibrationTolerance` is enabled, each gate check includes `sampleChecks` at every expected timestamp, with pass/fail/not-run and the requested measured error metrics. A not-run row explains whether evidence was absent, that time was not captured, or its active-track snapshot failed to match the plan.
